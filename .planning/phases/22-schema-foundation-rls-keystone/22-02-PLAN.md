## Trust Boundaries

|----------|-------------|
| any user → `user_profiles.role` UPDATE | The role column gates coach vs client; an unauthorized escalation bypasses the entire v1.5 access model |
| any user → `coach_profiles` table | Coach-visible identity surface; cross-user reads/writes would leak coach metadata |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-01 | E (Elevation) | direct UPDATE of `user_profiles.role` bypassing onboarding flow | mitigate | Existing `users_own_profile` `FOR ALL` policy (migration 001) requires `auth.uid() = id`, so users can ONLY update their own role; CHECK constraint restricts values to enum members. Phase 24 will add an onboarding SECURITY DEFINER RPC as the one sanctioned elevation path. Verified by `role.spec.ts` (CHECK rejection) + the pre-existing `users_own_profile` policy left intact. |
| T-22-01b | T (Tampering) | inserting role=invalid via SQL | mitigate | CHECK `role IN ('client','coach','both')`; verified by `role.spec.ts` test "CHECK rejects role=invalid". |
| T-22-02 (small surface) | I (Information disclosure) | cross-user read of `coach_profiles` (bio, kyc_docs) | mitigate | `coach_profiles_own FOR ALL USING (auth.uid() = user_id)` denies all reads except owner; Phase 24 will add a coach-discoverable `FOR SELECT` policy guarded by `is_coach_of`/published flag. Today, coach profiles are not yet public. Verified by `coach-profiles.spec.ts` test "User A only sees their own row in SELECT". |
