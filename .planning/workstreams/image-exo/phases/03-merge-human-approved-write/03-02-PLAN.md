    - Delay between attempt 1 and 2 is 500ms; between attempt 2 and 3 is 1000ms (exponential, base 500)
    - No delay is awaited after the final attempt fails
    - Explicit `attempts` / `baseDelayMs` arguments override the defaults

  <action>
Create `scripts/exercise-import/lib/retry.ts` with a top docstring stating: this is a deliberately minimal hand-rolled retry (03-RESEARCH.md "Don't Hand-Roll" exception for a 2-3 call-site need), it is intended for transient network-class failures around Storage uploads and Supabase writes ONLY, it must never be wrapped around pure in-memory work such as `capImage`/`capGif` (a resize failure is deterministic — retrying only burns time), and the MODULE SYSTEM CONSTRAINT from README.md "Module System" applies.

Export `RETRY_ATTEMPTS = 3` and `RETRY_BASE_DELAY_MS = 500` as named constants (mirroring `TIER2_THRESHOLD`'s exported-tunable pattern), and `withRetry<T>(fn: () => Promise<T>, attempts = RETRY_ATTEMPTS, baseDelayMs = RETRY_BASE_DELAY_MS): Promise<T>`.

Implementation contract: loop `attempt` from 0 to `attempts - 1`; `return await fn()` on success; on throw, store the error as `lastError` and, only if this is not the final attempt, await a `setTimeout` of `baseDelayMs * 2 ** attempt` milliseconds. After the loop, `throw lastError`. The last error must be the one thrown, so a caller's `error_message` reflects the most recent failure rather than a stale first one.

Create `scripts/exercise-import/lib/retry.test.ts` covering every case in `<behavior>`. There is no fake-timer precedent in this pipeline's existing tests, so introduce it cleanly here. Use `vi.fn()` call counts for the attempt-count assertions and assert on the identity of the propagated error (the third rejection, not the first).
