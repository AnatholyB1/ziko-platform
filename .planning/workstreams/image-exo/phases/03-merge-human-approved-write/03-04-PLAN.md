<objective>
Build the per-row unit of work the merge loop runs 1,324 times: cap and upload both media assets, snapshot the pre-UPDATE row, write the exercise, and return a classified outcome — with every failure contained to its own row.

Purpose: This is where IMPORT-03 (UPDATE in place preserving UUID, INSERT new, never DELETE), IMPORT-05 (legacy/ambiguous rows flagged, never auto-merged), MEDIA-03 (cap applied at the upload step), and MEDIA-04 (backup before write) are actually enforced. Isolating it from `merge.ts` means the ordering guarantees are unit-testable against a call-recording stub client, with no live credentials — which is the only automated proof available for this phase (real-DB integration is a manual supervised run, per 03-VALIDATION.md).
Output: `lib/merge-row.ts` and a test suite that asserts call ORDER, not just call presence.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dataset record fields → Supabase Storage object keys | Attacker-influenceable strings (`image`, `gif_url`, `media_id`) adjacent to path construction |
| dataset record fields → `public.exercises` columns | Untrusted values written to a live table referenced by `program_exercises` / `session_sets` |
| a single bad row → the other 1,323 rows | Blast-radius containment inside the batch |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-11 | Tampering | Storage object key construction in `storagePaths` | mitigate | Object keys are derived exclusively from the exercise UUID (report-supplied for matched rows, `crypto.randomUUID()` for new rows) with fixed filenames `thumb.png`/`animation.gif`; no dataset-supplied string is ever concatenated into a key. Grep-asserted that `media_id` and `record.image` do not appear in the upload path expression. |
| T-03-03 | Tampering | Filesystem read of dataset media | transfer | `merge-row.ts` never touches the filesystem; `readMediaBytes` is injected by `merge.ts` (plan 03-05), which applies Phase 2's `resolveInsideRoot()` containment plus the existing zod path regexes in `lib/types.ts` (threat T-02-01 carried forward) |
| T-03-12 | Tampering / Destruction | Irreversible overwrite of a production exercise row | mitigate | Full-row `exercises_merge_backup` insert is ordered strictly before the UPDATE and a failed backup aborts the row (index-order assertion in `merge-row.test.ts`); no `.delete()` call exists anywhere in the module (grep-asserted); the UUID is preserved so `program_exercises`/`session_sets` FKs stay intact |
| T-03-05 | Denial of Service (data integrity) | One bad row aborting or corrupting the batch | mitigate | `processRow` never rethrows; every failure resolves to a `MergeRowResult` with a bounded `errorMessage`; a failed `unmatched_new` insert returns `exerciseId: null` so the follow-up `exercise_import_log` write cannot violate its FK |
| T-03-06 | Tampering | Un-capped media reaching the public bucket | mitigate | Only the buffer returned by the injected `capImage`/`capGif` is passed to `upload`, asserted in `merge-row.test.ts` by comparing against the `readMediaBytes` buffer identity; bucket MIME allowlist (`image/png`, `image/gif`) and 2 MB limit from Phase 1 are a second layer |
</threat_model>
