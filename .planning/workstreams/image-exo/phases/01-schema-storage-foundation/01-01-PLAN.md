Columns added to `public.exercises` (existing table, `supabase/migrations/001_initial_schema.sql`):
- `image TEXT` — nullable, stores a relative storage path e.g. `{exercise_id}/thumb.png` (per D-02, not a full URL)
- `gif TEXT` — nullable, stores a relative storage path e.g. `{exercise_id}/animation.gif`

New table `public.exercise_import_log`:
- `id UUID PRIMARY KEY DEFAULT uuid_generate_v4()`
- `source_id TEXT NOT NULL` — dataset's original row identifier (dedupe/idempotency key for Phase 3)
- `exercise_id UUID REFERENCES public.exercises(id) ON DELETE SET NULL` — nullable, which row was touched (if any)
- `status TEXT NOT NULL CHECK (status IN ('matched', 'inserted', 'skipped', 'needs_review'))`
- `error_message TEXT` — nullable
- `processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`

New Storage bucket: `exercise-media` (`public: true`, `file_size_limit: 2097152`, `allowed_mime_types: ['image/png', 'image/gif']`)

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| mobile client (anon/authenticated) → Supabase Storage | Untrusted reads of `exercise-media` bucket objects (public bucket) |
| mobile client (authenticated) → Supabase PostgREST | Untrusted reads/writes against `public.exercises` and (once created) `public.exercise_import_log` |
| Phase 3 merge script (service-role, not built yet) → Supabase Storage + Postgres | Trusted writes — service-role key bypasses RLS entirely |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-01-01 | Tampering | `storage.objects` for `exercise-media` bucket | mitigate | No `CREATE POLICY` for INSERT/UPDATE/DELETE on `exercise-media` — writes only via service-role key, which bypasses RLS entirely. Verified by Task 1 acceptance criteria (grep confirms zero policy statements referencing the bucket). |
| T-01-02 | Tampering | `public.exercises.image` / `public.exercises.gif` columns | accept | Existing RLS policy `manage_own_exercises` (`001_initial_schema.sql`) already restricts UPDATE to `user_id = auth.uid()`. Global (`is_custom = false`) exercises have `user_id IS NULL`, so no authenticated client can ever match that predicate and write these columns on shared library rows — no new policy needed. |
| T-01-03 | Information Disclosure | `public.exercise_import_log` (auto-exposed via PostgREST once created) | mitigate | `ALTER TABLE public.exercise_import_log ENABLE ROW LEVEL SECURITY` with zero `CREATE POLICY` statements — deny-by-default blocks all anon/authenticated reads and writes; only the service-role key (bypasses RLS) can touch it. |
| T-01-04 | Information Disclosure | `exercise-media` public bucket (readable by anyone, no auth) | accept | Bucket contains only non-sensitive exercise thumbnails/GIFs sourced from a public dataset (Gym visual) — no PII, no user-generated content. Public readability is the explicit design goal (MEDIA-02), same precedent as the `avatars` bucket. |
| T-01-05 | Elevation of Privilege | `exercise-media` bucket upload surface (if service-role key were ever compromised) | mitigate | `file_size_limit: 2097152` (2MB) and `allowed_mime_types: ['image/png','image/gif']` bound what can be written even under a compromised service-role credential — defense-in-depth, not the primary control (the primary control is that no client-facing write policy exists at all). |
| T-01-SC | Tampering | `npx supabase` CLI (package supply chain, Task 2) | accept | Official, actively-maintained Supabase CLI package already used for this project's linked deployments (`supabase/.temp/linked-project.json` confirms prior legitimate use); invoked ephemerally via `npx`, not added as a new `package.json` dependency — no install/legitimacy audit gate applies. |

</threat_model>
