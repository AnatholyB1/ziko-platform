.planning/workstreams/image-exo/reports/match-report.json
  generated_at        ISO-8601 string
  dataset_commit      string          upstream SHA — provenance attached to the approval
  dataset_count       number
  production_count    number
  thresholds          { tier2: 0.87 }
  warnings            { duplicate_production_names: [ { normalized_name, exercise_ids[] } ] }
  counts              { matched, unmatched_new, unmatched_legacy, ambiguous }
  matched[]           { dataset_id, dataset_name, exercise_id, production_name, tier, score,
                        matched_on, field_conflicts[], phase3_status }
  unmatched_new[]     { dataset_id, dataset_name, body_part, equipment, target, phase3_status }
  unmatched_legacy[]  { exercise_id, production_name, production_name_fr, body_part,
                        equipment, target_muscle, phase3_status }
  ambiguous[]         { dataset_id, dataset_name, reason, candidates (max 3),
                        human_decision, phase3_status }

phase3_status values come from PHASE3_STATUS_HINT (lib/types.ts) and are exactly the Phase 1
exercise_import_log status enum (01-CONTEXT.md D-06): matched, inserted, skipped, needs_review.
The value skipped never appears in a Phase 2 report — it is Phase 3's resumability marker.

human_decision (D-10) is the reviewer's in-place edit surface on ambiguous rows: null, or
{ action: "match", exercise_id: "<uuid>" }, or { action: "insert_new" }, or { action: "skip" },
each with an optional note. Because D-08 mandates overwriting the same filename on every
re-run, mergePriorHumanDecisions MUST carry these edits forward or the reviewer's work is
destroyed by the next tuning iteration.
</interfaces>

    resurrect a phantom row. This is the D-08 safety net: overwriting a fixed filename must
    never destroy reviewer work.

      "none" line when there are none
    - an "Ambiguous — needs your decision" section rendering EVERY ambiguous row (never
      truncated — this is the section the reviewer actually works through), each showing the
      dataset name, its up-to-3 candidates with score, tier and matched_on, and the literal
      JSON snippet to paste into human_decision
    - a "Matched with field conflicts" section listing only matched rows whose field_conflicts
      array is non-empty
    - sample sections for matched, unmatched_new and unmatched_legacy: first 20 rows followed
      by a line reading "... and N more — see match-report.json"
    - a closing "How to approve" block: edit human_decision on ambiguous rows in
      match-report.json, then commit both files; the committed report is what Phase 3 treats

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| script process → Supabase Postgres | Credentialed production access crosses here (read-only by construction) |
| report artifact → Phase 3 write privileges | Everything in match-report.json becomes an instruction a privileged merge script later executes |
| prior report file on disk → new report | A previously-written (possibly hand-edited) JSON file is parsed as input |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03 | Tampering | `match.ts` write surface | mitigate | Grep gates assert insert/update/upsert/delete/rpc/storage call sites are absent from the entrypoint, and `lib/supabase-client.ts` (plan 02-02) has an automated zero-write assertion on the stubbed client. Roadmap SC #4. |
| T-02-02 | Elevation of Privilege | Supabase credentials in `match.ts` | mitigate | Client is built only via `createReadOnlyClient()` (publishable key); `SUPABASE_SERVICE_KEY` is grep-asserted absent. Read scoping delegated to the existing `read_exercises` RLS policy (ASVS V4). |
| T-02-11 | Tampering | prior `match-report.json` parsed as input | mitigate | Parsed inside try/catch; a corrupt file degrades to `null` with a printed warning. Only the `human_decision` field is carried forward from it — no prior category, count, or match result is ever trusted, so a tampered prior report cannot manufacture a fake `matched` row. |
| T-02-12 | Repudiation | approving a report without knowing what it was built from | mitigate | `dataset_commit`, `generated_at`, `production_count`, and `thresholds.tier2` are stamped into both artifacts, and both are committed to git — the approval is attributable to an exact upstream SHA and threshold |
| T-02-13 | Information Disclosure | report committed to git | accept | The report contains exercise names, UUIDs, and taxonomy fields only — no user data, no PII, no secrets. `.planning/` is deliberately versioned (D-07). |
| T-02-07 | Tampering | `git rev-parse` invocation | mitigate | `spawnSync` argv array, no `shell: true`, path from a constant — grep-asserted |
</threat_model>
