  <action>
    Examine every row in the report whose `tier` is `tier2`, sorted by ascending score. For each,
    judge by name whether the pairing is a genuine rename or a false positive.

    Decision rule:
    - Any tier2 pairing that is NOT the same exercise is a false positive. Raise TIER2_THRESHOLD
      just above that pair's score, re-run match, and re-examine. Repeat until zero false
      positives remain in `matched`.
    - If there are zero false positives at 0.87, keep 0.87. Do not lower it to harvest more
      matches unless you can name specific pairs below the threshold that are genuine renames,
      and record those names in the SUMMARY as the justification.
    - Genuine renames that end up below the threshold are NOT a failure: they land in
      `ambiguous` or `unmatched_new` where a human resolves them. Precision beats recall here
      because Phase 3 turns a `matched` row into an in-place UPDATE of a live production row.

    For every false positive found, add a regression test to `lib/matcher.test.ts` using the two
    real names, asserting that pair does NOT produce a `matched` row at the final threshold. Do
    the same for any genuine rename you deliberately admitted, asserting it DOES match.

    After the final threshold is chosen, re-run fetch (cache reuse, no `--refetch` needed),
    match, and the checker, then verify the whole unit suite is still green. Record in the
    SUMMARY: the final threshold, how many iterations were run, the specific pairs that drove
    each change, and the before/after category counts.

    Only `TIER2_THRESHOLD` is in scope for tuning. Do not weaken the Tier 1 exact-match rule,
    do not promote Tier 3 results to `matched`, and do not relax the `is_custom = false` filter.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| live upstream dataset → local disk | Real third-party content is fetched and trusted as data for the first time in this phase |
| live production database → script | Real credentials are used against real production data |
| generated report → Phase 3 write privileges | Human approval is the only control standing between a match decision and a production UPDATE |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03 | Tampering | live production data during the dry run | mitigate | Zero-write is enforced three ways: grep gates on source, the stubbed-client zero-write test from plan 02-02, and the Task 3 checkpoint's explicit row-count confirmation on `exercises`, `exercise_import_log`, and `coach_exercises` |
| T-02-09 | Tampering | a false-positive `matched` row reaching Phase 3 | mitigate | Task 2 requires examining every tier2 pairing by name and raising the threshold until zero false positives remain, with each one locked out by a regression test; Task 3 adds an independent human review gate before the report counts as approved |
| T-02-14 | Information Disclosure | Supabase credentials leaking into a committed artifact | mitigate | `backend/api/.env.local` is already covered by the root `.gitignore` `.env.*` rule; the task instructions forbid echoing its contents into the SUMMARY, the report, or any log |
| T-02-01 | Tampering | live upstream content differing from the researched snapshot | mitigate | `fetch.ts` re-validates every record through zod and re-verifies file counts on this real run; `dataset_commit` is stamped into the report so the approval is bound to an exact upstream SHA |
| T-02-13 | Information Disclosure | report committed to git | accept | Contains exercise names, UUIDs, and taxonomy fields only — no PII, no secrets |
