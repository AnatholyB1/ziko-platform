<!-- The tier contract this plan implements. Locked here; plan 02-05 consumes it verbatim. -->

Tier 1 (exact, high precision) — resolves D-01 + D-02
  1a. normalize(dataset.name) === normalize(production.name)          → matched_on: 'name'
  1b. normalize(dataset.name) === normalize(production.name_fr)       → matched_on: 'name_fr'
  The dataset has NO French name field (schema-verified). D-01's intent is realized by
  comparing the dataset's single English name against BOTH production columns — 1b catches
  French fitness loanwords used as-is ("squat", "burpee", "crunch"). 1a is tried first.
  Disagreeing body_part / equipment / target does NOT downgrade the row (D-02): production
  `name` is the strong signal. The disagreement is recorded in `field_conflicts` so the
  reviewer sees it.
  Collision rule: if 1a/1b resolve to MORE THAN ONE production row, the dataset exercise is
  ambiguous with those rows as candidates — never an arbitrary pick.

Tier 2 (fuzzy, conservative) — resolves D-03
  similarityRatio(normalized names) >= TIER2_THRESHOLD (0.87, from lib/normalize.ts)
  against both production.name and production.name_fr. Exactly one candidate at or above
  threshold → matched (tier: 'tier2', score recorded). Two or more → ambiguous with the
  top 3 by score (D-09). Zero → fall through to Tier 3.

Tier 3 (attribute overlap, never confident) — resolves D-04
  Score = count of agreeing fields among:
    dataset.body_part === production.body_part
    dataset.equipment === production.equipment
    dataset.target    === production.target_muscle
  (all compared case-insensitively, trimmed). Requires at least 2 of 3 to produce a candidate.
  Tier 3 output is ALWAYS categorized `ambiguous`, NEVER `matched` — multiple distinct
  exercises legitimately share body_part+equipment+target (IMPORT-02 precision-first mandate).

Categories → Phase 1 `exercise_import_log` enum (via PHASE3_STATUS_HINT in lib/types.ts):
  matched          → 'matched'
  unmatched_new    → 'inserted'
  unmatched_legacy → 'needs_review'   (Phase 3 decides untouched-vs-flagged using FK history, IMPORT-05)
  ambiguous        → 'needs_review'

Exclusions (roadmap SC #3): production rows arrive pre-filtered to `is_custom = false` by
`fetchAllProductionExercises`; `coach_exercises` is never queried anywhere in this pipeline.
The matcher takes rows as input and must not re-implement or weaken these filters.

  <action>
    Create `lib/matcher.ts`. Pure functions only: no `createClient`, no `fs`, no `process.env`,
    no `console` side effects other than nothing at all (the entrypoint does the printing).

    Export:
    - `findDuplicateNames(production: ProductionExercise[])` — uses `groupByNormalizedName` over
      `name` and separately over `name_fr`, returning
      `Array<{ normalized_name, exercise_ids: string[] }>` for every group of size > 1.
      This is the Pitfall-4 safety check: it makes a latent production data-quality issue
      visible in the report rather than letting a `Map.set()` collision silently drop rows.
      It must NOT throw or filter anything — reporting only.
    - `buildNameIndex(production: ProductionExercise[])` — returns
      `{ byName: Map<string, ProductionExercise[]>, byNameFr: Map<string, ProductionExercise[]> }`.
      Values are ARRAYS, never single rows, precisely so duplicates cannot be lost.
    - `tier1Match(dataset, index)` — returns `{ rows: ProductionExercise[], matched_on: 'name' | 'name_fr' }`.
      Try `byName` first; if it yields zero rows, try `byNameFr`. Return the array as-is
      (length 0, 1, or >1) — the caller decides matched vs ambiguous.
    - `tier2Match(dataset, production)` — returns candidates at or above `TIER2_THRESHOLD`,
      scored against both `name` and `name_fr` (keep the higher score and its `matched_on`),
      sorted by score descending. Skip production rows already consumed by Tier 1.
    - `tier3Candidates(dataset, production)` — attribute-overlap candidates with at least 2 of 3
      agreeing fields, scored as `agreeing / 3`, sorted descending, `matched_on: 'attributes'`.
    - `computeFieldConflicts(dataset, production): string[]` — returns the subset of
      `['body_part', 'equipment', 'target']` whose values disagree (case-insensitive, trimmed;
      a null/empty production value counts as a conflict only if the dataset value is non-empty —
      label those as e.g. `body_part:missing-in-production` so the reviewer can tell a genuine
      disagreement from a gap).
    - `categorizeAll(dataset: DatasetExercise[], production: ProductionExercise[])` — the
      orchestrator. Returns
      `{ matched, unmatched_new, unmatched_legacy, ambiguous, duplicate_production_names }`.
      Algorithm:
      1. `duplicate_production_names = findDuplicateNames(production)`
      2. Build the index; maintain a `Set<string>` of consumed production `id`s
      3. First pass over ALL dataset records: Tier 1 only. Exactly one row → matched (tier
         'tier1', score 1, `field_conflicts` from `computeFieldConflicts`), mark consumed.
         More than one row → ambiguous with those rows as candidates (top 3, score 1).
         Running Tier 1 to completion before Tier 2 is deliberate: a fuzzy match must never
         steal a production row that some other dataset record matches exactly.
      4. Second pass over the remaining dataset records: Tier 2 against unconsumed production
         rows. Exactly one candidate → matched (tier 'tier2', its score, field conflicts),
         mark consumed. Two or more → ambiguous with the top 3.
      5. Third pass over what is still unresolved: Tier 3 against unconsumed rows. Any
         candidate → ambiguous (top 3, `reason: 'attribute-overlap-only'`). Zero candidates →
         `unmatched_new`.
      6. `unmatched_legacy` = every production row whose id is not in the consumed set and that
         does not appear as a candidate on any ambiguous row. Production rows that appear only
         as ambiguous candidates go to neither bucket — record them nowhere else, so no row is
         double-counted between `ambiguous` candidates and `unmatched_legacy`.
      7. Every ambiguous row gets `human_decision: null` (D-10 — the reviewer fills it in place).
      Invariant that must hold and that the tests assert:
      `matched.length + unmatched_new.length + ambiguous.length === dataset.length`
      and no production id appears in both `matched` and `unmatched_legacy`.
  </action>
