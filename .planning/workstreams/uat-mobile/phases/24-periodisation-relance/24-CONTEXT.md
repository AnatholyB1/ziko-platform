# Phase 24 - CONTEXT (Periodisation & relance automatique)

Branche `phase/24-periodisation` (base `milestone/v1.20`, P23 deja merge). Exigences ATEL-07, ATEL-08, ATEL-09. Decisions utilisateur deja prises (non rediscutees) : un seul programme actif (P7) ; a la fin d'un programme l'atelier se relance AUTOMATIQUEMENT avec les resultats ; regle NON PUNITIVE (aucune penalite) ; appels IA automatiques ABSORBES (pas de credit) avec plafond journalier et journalises `ziko_ai_cost_log` ; bouton plein = `getActionPrimary(theme)`. Aucune maquette lot-A pour la suite/le bilan (le contrat lot-A s'arrete a A15) : UI minimale construite avec les composants et tokens existants, a valider visuellement (voir G-6).

## Decisions verrouillees (D-xx)
- D-01 Suite ordonnee = colonnes sur `ziko_ai_generated_programs` (`sequence_id`, `sequence_position`, `started_at`, `completed_at`, `results jsonb`) + table `ziko_program_sequences` (id, user_id, name, goal). Pas de nouvelle table de liaison : un programme appartient a au plus une suite, position unique par suite (index unique partiel). Seuls les programmes IA/atelier entrent dans une suite (les programmes coach/crees n'ont pas de colonne : hors scope, voir Hors scope).
- D-02 "Un seul actif" : inchange, le chemin unique reste la RPC P7 `ziko_set_active_program`. La suite n'ajoute AUCUN second mecanisme d'activation. A la fin d'un programme le backend le passe `is_active=false` + `completed_at` ; le programme suivant n'est JAMAIS active automatiquement (propose, inactif ; l'utilisateur l'active par le chemin P7).
- D-03 `started_at` pose par un trigger BEFORE INSERT/UPDATE sur `ziko_ai_generated_programs` a la premiere activation (independant de la RPC P7, qui n'est pas redefinie). Programmes actifs avant la migration : `started_at` = NULL, repli sur `created_at` (cote backend, `effectiveStart`).
- D-04 Fin de programme (pur, `periodization/progress.ts`) : fini quand `now >= started_at + weeks_count * 7 jours` OU quand les seances terminees dans la fenetre atteignent `weeks_count * days_per_week`. Les seances manquees ne retardent ni ne penalisent : la fin est calendaire (D-04 neutre). Seances comptees = `ziko_workout_sessions` de l'athlete avec `ended_at` non nul dans `[started_at, now]` (les seances de programmes IA n'ont pas de `program_id` lisible : la fenetre de dates est le seul lien disponible, voir "Non prouve").
- D-05 Resultats (pur, `periodization/results.ts`) : seances faites/prevues, adherence %, volume total, e1RM (Epley, meme formule que `context.ts`) debut vs fin par exercice (comparaison premiere moitie / seconde moitie de la fenetre), records. Stockes dans `ziko_ai_generated_programs.results`. Langage neutre uniquement : "Programme termine", jamais "echec/rate/manque". Une adherence faible produit un conseil de reprise (`reentry`), pas un malus.
- D-06 Non punitif, garanti par construction : la relance n'importe ni `creditService`, ni gamification, ni serie ; elle ne lit/ecrit que programmes, brouillons, conversations, `ziko_ai_cost_log`. Test dedie : aucune ecriture hors tables attendues. L'utilisateur peut ignorer la relance (status `dismissed`) sans consequence.
- D-07 Relance en 2 temps, idempotente par `ziko_program_relaunches.program_id UNIQUE` : (1) `POST /ai/workshop/relaunch/check` = detection + cloture du programme + creation de la relance + du brouillon liees (rapide, sans IA) ; (2) `POST /ai/workshop/relaunch/:id/propose` = UN appel IA automatique (`generateText`, memes outils de l'atelier, meme prompt + bloc resultats) qui ecrit le brouillon du programme suivant. Compare-and-set `pending -> proposing` (reprise apres 3 min) pour qu'un double appel ne paie pas deux fois. Ecrit un message systeme + la reponse dans la conversation (historique de l'atelier).
- D-08 Credits : AUCUN `creditCheck/creditDeduct` sur `propose` (appel automatique absorbe, comme P14). Plafond : `PROGRAM_RELAUNCH_DAILY_CAP = 1` appel par utilisateur et par jour UTC (compte `ziko_ai_cost_log` `source='program_relaunch'`). Plafond atteint ou echec du modele : la relance reste `pending` SANS proposition ; l'atelier s'ouvre quand meme avec le bilan et l'utilisateur continue a la main (tours payes normalement par `/stream`). Cout journalise meme en echec partiel (`logAutonomousCost`).
- D-09 Declencheur : l'app appelle `check` a l'ouverture de l'onglet Seance (pas de cron : meme choix que P14, aucun fichier `vercel.json` modifie), puis `propose` en tache de fond si une relance est `pending`. L'atelier ouvert via `?relaunch=<id>` appelle `propose` (idempotent) et charge le brouillon.
- D-10 Publication : `publishDraft` d'un brouillon issu d'une relance rattache le programme enregistre a la suite (`sequence_id` herite, `sequence_position = max + 1`), INACTIF. Quand `check` cloture un programme sans suite, il cree la suite (`name` = nom du programme, position 1) avant de la prolonger.
- D-11 Suite visible : `GET /ai/workshop/sequence` renvoie la suite courante ordonnee avec statut calcule (`done` / `active` / `next` / `planned`) et un resume des resultats. Ecran mobile `workout/sequence.tsx` (frise verticale + bilan du dernier programme termine + bouton `Preparer la suite` quand une relance est en attente) ; bandeau d'entree sur l'onglet Seance.

## Gray areas (reco marquee)
- G-1 [A CONFIRMER] Declencheur : a l'ouverture de l'app (D-09) vs cron quotidien (couvre aussi un athlete qui n'ouvre pas l'onglet Seance). Reco : ouverture d'app maintenant (zero infra), cron plus tard si besoin (la logique `runRelaunchCheck` est deja isolee et reutilisable).
- G-2 [A CONFIRMER] Plafond : 1 relance automatique par utilisateur et par jour. Valeur dans `periodization/limits.ts`.
- G-3 [A CONFIRMER] Fin "calendaire OU toutes les seances faites" (D-04). Alternative : exiger les deux ; rejetee car un athlete qui termine tot attendrait sans raison.
- G-4 [A CONFIRMER] Le suivant n'est jamais active automatiquement (D-02) : l'utilisateur confirme. Reco : oui (conforme "un seul actif, choix de l'utilisateur" P7).
- G-5 [A CONFIRMER] Programmes coach / crees (table `ziko_workout_programs`) hors suite en P24 : leur "fin" n'a pas de `started_at` fiable. Reco : traiter avec P25 si Mon coach le demande.
- G-6 [A CONFIRMER] Pas de maquette : ecran `sequence.tsx` + bandeau a valider visuellement (lot design a commander si la direction du rendu est refusee).
- G-7 Appel IA automatique sans outil de recherche web : `propose` ne passe PAS `workshop_web_search` (cout/latence, pas d'interaction utilisateur pour arbitrer) ; skills et contexte restent disponibles.
