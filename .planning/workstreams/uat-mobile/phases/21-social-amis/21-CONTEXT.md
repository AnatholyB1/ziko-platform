## Gray areas (reco + `[A CONFIRMER]`)
- **G-01 Le profil public n'est pas lisible aujourd'hui (constat bloquant).** `apps/mobile/app/(app)/profile/[userId].tsx` lit `ziko_user_profiles` d'un autre utilisateur, or la seule policy est `users_own_profile (auth.uid() = id)` (schéma portfolio l.2308) : le profil d'un ami ne se charge pas ; le bouton `Suivre` n'est qu'un `useState` local (rien n'est écrit) ; `Défis` et `Abonnés` valent `—`. Niveau/XP (`ziko_user_gamification`), badges (`ziko_user_badges`, policy `user_badges_own`), séries de sets/PR (`own_session_sets`) sont aussi illisibles côté ami. Reco `[A CONFIRMER]` : **un RPC `ziko_get_public_profile(p_user uuid)` SECURITY DEFINER** qui s'appuie sur `auth.uid()` (jamais un id appelant passé en paramètre), renvoie un `jsonb` borné aux champs du contrat + l'état de relation. Alternative écartée : élargir les policies SELECT de 5 tables (surface d'exposition bien plus large). Visibilité : voir Q-P21a.
- **G-02 Source unique de l'état d'amitié.** Aujourd'hui 3 implémentations divergentes : `FriendsScreen.tsx` (statut calculé à la main), `SearchOverlay.tsx` (insert direct, helper P2), `store.ts` `sendFriendRequest` (**ignore l'erreur d'insert** et ne renvoie rien). Reco : un seul module `friendRelation` (pur, testé) + RPC `ziko_search_users_with_status(query, limit)` qui renvoie `relation` (`none|sent|received|friend`) calculé côté serveur avec `auth.uid()`. L'actuel `ziko_search_users_fuzzy(search_query, calling_user_id, …)` est exécutable par `anon` et prend l'id appelant en paramètre (spoofable) : ne pas l'étendre, le laisser en place pour compatibilité (nouvelle fonction dans une nouvelle migration).
- **G-03 Cas transmis par P2 (demande croisée).** A->B puis B cherche A : l'insert B->A passe (clé unique orientée) et crée 2 lignes. Reco : RPC `ziko_send_friend_request(p_addressee uuid)` atomique : refuse soi-même, no-op si déjà demandée (renvoie l'état), **accepte** si la demande inverse existe (course), sinon insère ; un index unique **sur la paire non ordonnée** garantit l'unicité. L'UI montre déjà `Accepter` en cas de demande reçue (D13), l'auto-accept ne couvre que la course. Prérequis de migration (dédoublonnage des paires croisées existantes) : voir Q-P21b.
- **G-04 Faille RLS à fermer.** `friendships_update` autorise **les deux parties** à mettre à jour la ligne (`requester` ou `addressee`) : un demandeur peut donc s'auto-accepter (`status = 'accepted'`). Reco : restreindre l'UPDATE à `addressee_id = auth.uid()` avec `WITH CHECK (status = 'accepted')` (nouvelle migration ; `DELETE` reste ouvert aux deux parties : annuler/refuser/retirer). Test RLS ajouté (`npm run test:rls`).
- **G-05 Compteur `abonnés`** après fusion Suivre/ami : voir Q-P21c.
- **G-06 `série`** : réutiliser la définition déjà calculée par `apps/mobile/app/(app)/profile/index.tsx` (habitudes + séances) plutôt qu'en inventer une ; le RPC la calcule en date locale du **profil consulté** (documenter le fuseau, défaut `Europe/Paris` côté SQL). Décision technique, builder documente.
- **G-07 Défis en commun** : jointure `ziko_challenge_participants` (`cp_read USING (true)`) sur les deux ids ; max 2 affichés. Pas de migration pour la lecture.
- **G-08 Retrait d'ami / annulation** : `DELETE` sur `ziko_friendships` (policy existante). Pas de blocage/signalement dans ce lot (l'alerte "Signaler, bloquer…" actuelle est un placeholder) : à retirer ou masquer, `[A CONFIRMER]`.
