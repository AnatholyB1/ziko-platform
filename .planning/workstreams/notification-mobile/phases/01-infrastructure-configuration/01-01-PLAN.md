    interface NotificationPayload { recipientUserId: string; category: 'coach'|'workout'|'gamification'|'health'|'system'; type: string; title: string; body: string; data?: { url?: string; [key: string]: unknown }; idempotencyKey: string; }

    Implement send(payload: NotificationPayload): Promise<{ sent: boolean; reason?: string }>:
    1. Query notification_preferences via supabaseAdmin. If row not found, treat as all-defaults-enabled (push_enabled=true). If push_enabled=false or the specific category column (coach_enabled, workout_enabled, etc.) is false → return { sent: false, reason: 'preference_disabled' }
    2. Quiet hours check (per D-09): fetch quiet_hours_start, quiet_hours_end, timezone_offset from preferences. Compute user local UTC hour = (currentUTCHour + timezone_offset) % 24. If hour in [quiet_hours_start..quiet_hours_end) (handling midnight wrap) → return { sent: false, reason: 'quiet_hours' }
    3. Attempt idempotency INSERT via supabaseAdmin into notification_log: INSERT ... (idempotency_key, user_id, category, type, title, body, data, status='pending') ON CONFLICT (idempotency_key) DO NOTHING RETURNING id. If no row returned (conflict) → return { sent: false, reason: 'duplicate' }
    4. Fetch active tokens: SELECT token FROM notification_tokens WHERE user_id = recipientUserId AND is_active = true (via supabaseAdmin)
    5. Filter: keep only tokens where Expo.isExpoPushToken(token) is true. For invalid tokens, UPDATE notification_tokens SET is_active=false WHERE token = invalidToken (via supabaseAdmin).
    6. Chunk valid tokens into batches of ≤100 using expo.chunkPushNotifications(). For each chunk, call expo.sendPushNotificationsAsync(messages) where each message is: { to: token, title, body, data, channelId: category, sound: 'default', badge: 1 }
    7. Process tickets: collect all ticket.id values where ticket.status === 'ok'. For tickets where ticket.status === 'error' and ticket.details.error === 'DeviceNotRegistered', update that token to is_active=false via supabaseAdmin.
    8. UPDATE notification_log SET status='sent', receipt_ids=[...ticketIds], sent_at=NOW() WHERE idempotency_key=payload.idempotencyKey (via supabaseAdmin)
    9. Return { sent: true }

    Implement sendBatch(payloads: NotificationPayload[]): calls send() for each payload in sequence. Returns { sent: number, failed: number }.

    Implement processReceipts(receiptIds: string[]): chunks receipt IDs using expo.chunkPushNotificationReceiptIds(), calls expo.getPushNotificationReceiptsAsync() per chunk. For each receipt: if status==='ok' → UPDATE notification_log SET status='delivered'; if details.error==='DeviceNotRegistered' → UPDATE notification_tokens SET is_active=false AND UPDATE notification_log SET status='failed', error_code='DeviceNotRegistered'.

    Export as: export const notificationService = { send, sendBatch, processReceipts };

    CRITICAL: All Supabase reads/writes in this service use supabaseAdmin (service key), NEVER the user JWT. This is required because the service sends to users other than the caller (e.g. coach sending to athlete).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mobile → POST /notifications/token | Untrusted token string from device crosses into DB |
| server → Expo Push API | Internal service sends payloads on behalf of users |
| server → Supabase notification_tokens | Admin client bypasses RLS — must only be used server-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | POST /notifications/token | mitigate | Validate token matches /^ExponentPushToken\[.+\]$/ before UPSERT; 400 on invalid format |
| T-01-02 | Spoofing | notification_tokens admin write | mitigate | Service key only used server-side (in notificationService.ts and route handler); never sent to mobile |
| T-01-03 | Repudiation | notification_log idempotency | mitigate | ON CONFLICT (idempotency_key) DO NOTHING prevents duplicate log rows; log is immutable from user side |
| T-01-04 | Information Disclosure | notification_log RLS | mitigate | SELECT policy enforces auth.uid() = user_id; no INSERT policy prevents user-created fake logs |
| T-01-05 | Denial of Service | POST /notifications/token flood | accept | Rate limiting is Vercel edge concern; single UPSERT per (user_id, device_id) is idempotent and safe |
| T-01-SC | Tampering | npm install expo-server-sdk | mitigate | expo-server-sdk is the official Expo-team maintained SDK; verify via npmjs.com/package/expo-server-sdk before install |
</threat_model>
