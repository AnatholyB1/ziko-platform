<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hono route → notificationService (athlete) | Authenticated athlete triggers a push to themselves — self-send |
| Hono route → notificationService (coach) | Authenticated athlete triggers a push to a different user (coach) — cross-send |
| notificationService → Expo Push API | Backend sends on behalf of two users to external service |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-02-01 | Spoofing | POST /links/redeem | mitigate | Route protected by authMiddleware; athleteId = c.get('auth').userId (from JWT), not from request body. Coach ID sourced from result.link.coach_id (DB record), not from request. |
| T-02-02-02 | Repudiation | Bidirectional deduplication | mitigate | Two distinct idempotencyKeys (invitation_accepted_athlete_*, invitation_accepted_coach_*) ensure each send is independently deduplicated. Replaying the same code after redemption hits the already-redeemed guard before the push block. |
| T-02-02-03 | Information Disclosure | Coach push body — athlete name | accept | Athlete name from user_profiles is shown to the coach who already has a coaching relationship. No third party sees the name. Acceptable disclosure within the relationship. |
| T-02-02-04 | Denial of Service | Concurrent sends | accept | Only two concurrent sends per redemption event. Promise.allSettled() isolates failures. No amplification risk. |
</threat_model>
