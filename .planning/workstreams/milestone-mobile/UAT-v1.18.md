## Bugs / observations (none blocking, no fix applied)
1. LOW - duplicate cron deliveries are reported as `failed`. Repro: one due athlete, fire 3 concurrent `POST /coaching-engine/cron/weekly-review` (Bearer CRON_SECRET) -> two responses are `{"processed":2,"succeeded":0,"skipped":1,"failed":1}`; the loser got RPC `duplicate` and `runWeeklyReview` returns `{ran:true,success:false}` which `routes.ts` counts under `failed` (no side effect: 1 decision / 1 reward / 1 push). Misleading monitoring noise; `duplicate` should count as `skipped`.
2. LOW / theoretical - an athlete whose due week already has a decision (`already_recorded`) is `skipped` but `next_review_due_at` is not advanced, so each cron rescans them forever (reproduced only by manually re-opening a reviewed athlete; the normal RPC moves the date +7 d).

## Process disclosure
- First backend start used an ESM resolve hook that did not intercept (tsx runs the backend as CJS): 5 `generateObject` calls reached `api.anthropic.com` with a dummy key (HTTP 401, no data) before I noticed; I then pointed `ANTHROPIC_BASE_URL` at a dead port as a safety net and replaced the hook by a CJS `Module._load` preload.
- In the next run `expo-server-sdk` (loaded by dynamic `import()`) was still real: 7 sends with fake `ExponentPushToken[uat-uN]` tokens were attempted against exp.host (no device, no real token). That DB state was wiped (reseed) and the whole sequence re-run clean with the Expo stub AND `EXPO_BASE_URL` on a dead port; the final evidence above comes only from the clean run (pushes recorded in `push.jsonl`, `receipt_ids` populated by the stub).
- Teardown: servers on :3130/:3131/:54421/:54422 and Postgres :54420 stopped, machine lock removed.
