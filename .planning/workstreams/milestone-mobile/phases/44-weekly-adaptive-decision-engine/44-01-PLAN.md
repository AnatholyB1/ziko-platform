CRITICAL — overload hazard: in PostgreSQL, `CREATE OR REPLACE FUNCTION` with a different argument count creates a NEW overload rather than replacing the old one. Adding `p_new_goal JSONB DEFAULT NULL` to the existing 9-arg function would leave both a 9-arg and a 10-arg `record_athlete_decision`, and every existing 9-named-param call from `tools/onboarding.ts` / `tools/onboarding-retroactive.ts` would then fail as ambiguous. Therefore this migration MUST begin with an explicit `DROP FUNCTION IF EXISTS public.record_athlete_decision(UUID, TEXT, DATE, TEXT, TEXT, JSONB, JSONB, TEXT, JSONB);` (the exact 9-type signature) before creating the 10-arg version. 44-PATTERNS.md's sketch omits this drop — do not follow it on that point.

Then `CREATE OR REPLACE FUNCTION public.record_athlete_decision` with the original nine parameters in the original order plus a tenth, `p_new_goal JSONB DEFAULT NULL`. Keep `RETURNS JSONB`, `LANGUAGE plpgsql`, `SECURITY DEFINER`, `SET search_path = public, pg_temp`. Declare `v_decision_id UUID`, `v_goal_id UUID`, `v_rows INTEGER`.

| Boundary | Description |
|----------|-------------|
| Backend service-role client → Postgres | Backend code holds the service-role key; without table-level REVOKEs, that key can write `athlete_goals` directly and bypass the grounded-decision RPC door |
| Authenticated athlete JWT → PostgREST | An athlete could attempt direct REST writes to `athlete_goals` if RLS/grants are permissive |
| Local shell / CI runner → remote Supabase project (admin plane) | Task 3 holds `SUPABASE_ACCESS_TOKEN` and `SUPABASE_DB_PASSWORD`, a strictly higher privilege than anything else in the phase |
