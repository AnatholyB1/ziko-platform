Create `backend/api/src/coaching-engine/routes.ts` exporting a Hono router named `coachingEngineRouter` plus `export const maxDuration = 60;`.

Do not depend on Vercel Fluid Compute — its enablement on this project is unverified (44-RESEARCH.md assumption A4). `maxDuration = 60` matches the three existing inline precedents in this backend and needs no `functions` block in `vercel.json`.

Define `POST /cron/weekly-review` FIRST, before any `router.use('*', authMiddleware)` line. Its handler reads `c.req.header('authorization')` and `process.env.CRON_SECRET`; when the secret is set and the header is not exactly `Bearer ` followed by that secret, return `c.json({ error: 'Unauthorized' }, 401)`. Route-definition order is load-bearing: a cron guarded after `authMiddleware`, or left unguarded, lets anyone fabricate weekly decisions and, downstream in Phase 45, rewards.

The cron handler then builds a client via `clientForUser()` from `./db.js` and scans for eligible athletes: select `user_id` from `athlete_state` where `next_review_due_at` is not null and is at or before now, and `status` is not `'paused'`, ordered by `next_review_due_at` ascending, with `.limit(40)`.

Process that list in sequential chunks using `Promise.allSettled` over each chunk of 8. Never write a sequential per-athlete `for` loop with an LLM call in its body — `monitor-cron`'s loop is safe only because it makes zero model calls, whereas this loop makes one `generateObject` call per athlete at roughly 1-3s each, so 40 sequential athletes would exceed the 60s ceiling. Declare the batch size (40) and the concurrency (8) as named module-level constants with a comment deriving them from the 60s budget, so they are tunable in one place as athlete volume grows.

Call `runWeeklyReview(userId, 'weekly_review_cron')` for each athlete. Return `c.json({ processed, succeeded, skipped, failed })` — counts only, never athlete ids and never decision content in the response body.

Athletes beyond the 40-row cap are deliberately left for the next trigger: their `next_review_due_at` stays in the past, so they are picked up by their own next app open (the primary lazy trigger) or the following Sunday's cron. That is catch-up latency, not data loss, and it matches the milestone's non-punitive posture.

After the cron route, add `router.use('*', authMiddleware);` and then define `GET /review-check`. Its handler reads `const { userId } = c.get('auth')` and the bearer token from the `Authorization` header, then calls `waitUntil()` with an async IIFE that awaits `runWeeklyReview(userId, 'app_open_fallback', userToken)` and attaches a `.catch` that console.errors. An unhandled rejection inside `waitUntil` must never surface as a 500 on a fire-and-forget endpoint. The handler returns `c.json({ ok: true })` immediately, before the review runs — do not await the review and do not return its result.

Require no request body and no query parameter on `/review-check`: bare auth is sufficient (44-RESEARCH.md Open Question 3). Locale and copy concerns belong to the mobile overlay, which reads `athlete_state` directly under RLS.

The due-check itself stays inside `runWeeklyReview`, which returns `{ ran: false, reason: 'not_due' }` cheaply before any model call — this route is a thin dispatcher with no duplicated due logic.

Every relative import ends in `.js`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public internet → `/coaching-engine/cron/weekly-review` | Vercel cron paths are ordinary public HTTP routes; only the shared secret distinguishes the scheduler from an attacker |
| Athlete JWT → `/coaching-engine/review-check` | Any authenticated athlete can trigger background AI work by calling this endpoint repeatedly |
| Serverless invocation budget | The cron holds one LLM call per athlete inside a 60s ceiling |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-21 | Spoofing / Elevation of Privilege | `POST /cron/weekly-review` | mitigate | `CRON_SECRET` bearer check, defined before `router.use('*', authMiddleware)`, copied verbatim from the live `monitor-cron` pattern. A spec case asserts `authMiddleware` is never invoked on that path, which is the only reliable proof the guard sits ahead of it. |
| T-44-22 | Denial of Service / cost abuse | `GET /review-check` hammered by an authenticated athlete | mitigate | `runWeeklyReview` short-circuits on `not_due` and on `already_recorded` before any model call (plan 44-04, T-44-19), so repeated calls cost one cheap indexed read each. The route itself performs no model work. |
| T-44-23 | Denial of Service | 60s function ceiling exceeded by the cron | mitigate | Eligibility scan capped at `.limit(40)`, processed in `Promise.allSettled` chunks of 8; unreached athletes stay due and are picked up by the next trigger. `maxDuration = 60` is declared inline rather than assuming Fluid Compute is enabled. |
| T-44-24 | Information Disclosure | Cron response body | mitigate | The handler returns counts only — no athlete ids, no decision text, no rationale — so an attacker who somehow reaches the endpoint learns nothing about the athlete population |
| T-44-25 | Denial of Service | One athlete's failure aborting the whole batch | mitigate | `Promise.allSettled` per chunk; a rejection is counted as `failed` and the batch continues, asserted by spec case 10 |
| T-44-26 | Repudiation | Unhandled rejection inside `waitUntil` | mitigate | The IIFE attaches a `.catch` that logs; the response is already sent, so a background failure leaves the athlete due and retried rather than surfacing a false 500 |
| T-44-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this plan — 44-RESEARCH.md's Package Legitimacy Audit records zero new external packages for the phase. |
