# Plan 41-02: Final Fixture Audit + Skeleton/Empty/Error Sweep

## Goal
Remove the last known data fixture (`INITIAL_MESSAGES`) from `ai/chat.tsx`, explicitly handle the `SUGGESTIONS` constant, then run a grep-driven sweep to add missing loading/empty/error states to any screens that use `useQuery` but lack them.

## Tasks

### Task 1 — Remove INITIAL_MESSAGES from ai/chat.tsx; declare SUGGESTIONS out of scope

File: `apps/mobile/app/(app)/ai/chat.tsx`

**INITIAL_MESSAGES (data fixture — remove):**

At line ~40, there is a constant `INITIAL_MESSAGES: ChatMessage[]` with hardcoded message content. At line ~204, `useState<ChatMessage[]>(INITIAL_MESSAGES)` uses it as the initial state.

Steps:
1. Delete the entire `INITIAL_MESSAGES` constant declaration (the `const INITIAL_MESSAGES: ChatMessage[] = [...]` block).
2. Update the `useState` call at line ~204 to use an empty array literal:
   ```ts
   const [messages, setMessages] = useState<ChatMessage[]>([]);
   ```
3. Confirm no other reference to `INITIAL_MESSAGES` exists in the file.

This change is safe: the chat screen loads real conversation history from `ai_conversations`/`ai_messages` through the streaming API. `INITIAL_MESSAGES` was dead code.

**SUGGESTIONS (static UI constant — keep, exclude from audit):**

`chat.tsx` also contains `const SUGGESTIONS = ['Analyse ma séance d\'hier', ...]` at line ~75, rendered as suggestion chips in the empty-conversation state (line ~491). This is **NOT** a data fixture — it is a static UI affordance (a fixed list of example prompts, equivalent to a label or placeholder text). It does not come from an API and does not need to be replaced with a query. The fixture audit gate in Task 3 excludes it explicitly via `| grep -v SUGGESTIONS`.

### Task 2 — Grep-driven loading/empty/error sweep

Run the following command from the repo root to identify screens that use `useQuery` but have no loading guard:

```bash
grep -rL "isLoading\|isFetching" $(grep -rl "useQuery" apps/mobile/app plugins --include="*.tsx") 2>/dev/null
```

For each screen file surfaced by this command:

**Add loading guard** — at the top of the component's render body (after hooks, before JSX return):
```tsx
if (isLoading) return (
  <View style={{ flex: 1, justifyContent: 'center', alignItems: 'center' }}>
    <ActivityIndicator size="large" color="#FF5C1A" />
  </View>
);
```
Add `ActivityIndicator` to the React Native import if not already present.

**Add error state** — after the loading guard:
```tsx
if (isError) return (
  <ErrorScreen variant="network" onRetry={refetch} />
);
```

**Add empty state** — inside the query-dependent render branch, when `data` is empty:
```tsx
if (!data || data.length === 0) return (
  <EmptyState variant="no-data" title="Aucune donnée" />
);
```

Import pattern (add to existing import if not present):
```tsx
import { EmptyState, ErrorScreen } from '@ziko/ui';
```

Apply these patterns only to screens surfaced by the grep command above. Do not visit screens that already have `isLoading`/`isFetching` guards. Follow the exact same patterns already established in Phases 33–40 (visible in any recently-modified screen in `apps/mobile/app/(app)/` or `plugins/`).

**Exclusion — `_layout.tsx`:** Skip any layout file that surfaces in the sweep. Navigation layout files use `useQuery` for background session bootstrapping — adding loading guards to a layout breaks routing (the layout must render immediately and redirect). If `_layout.tsx` appears in the grep output, skip it entirely.

### Task 3 — Fixture audit gate

Run the fixture audit grep gate from the repo root. The goal is **zero** lines that represent true domain-data arrays (hardcoded arrays of objects containing domain fields like `id`, `message`, `title`, `name`).

The gate uses a tightened pattern that targets arrays-of-objects with domain fields, plus explicit exclusions for known legitimate UI constants:

```bash
grep -rn "const [A-Z_]\{4,\} = \[" apps/mobile/app plugins --include="*.tsx" \
  | grep -v SHADOW \
  | grep -v CARD \
  | grep -v MOTI \
  | grep -v CREDIT \
  | grep -v XP \
  | grep -v COIN \
  | grep -v TABS \
  | grep -v GOALS \
  | grep -v FAQ \
  | grep -v FILTER \
  | grep -v SUGGESTIONS \
  | grep -v ACTIVITIES \
  | grep -v GROUPS \
  | grep -v FRIENDS \
  | grep -v BADGES \
  | grep -v OPTIONS \
  | grep -v LABELS \
  | grep -v SECTIONS \
  | grep -v ITEMS \
  | grep -v DURATIONS \
  | grep -v EQUIPMENT \
  | grep -v LEVELS \
  | grep -v ZONES \
  | grep -v DAYS \
  | grep -v STEPS \
  | grep -v PLANNED \
  | grep -v INVITED \
  | grep -v STATIC \
  | grep -v STORE \
  | grep -v TYPES \
  | grep -v COLORS \
  | grep -v SIZES \
  | grep -v LINKS
```

All remaining hits (if any) after these exclusions are data fixtures requiring elimination. Use the fixture-elimination pattern from prior phases: remove the hardcoded array and replace with a `useQuery` call or empty `useState([])` as appropriate.

**Rationale for this gate approach:** The broader `grep -rn "const [A-Z_]\{4,\} = \["` pattern matches ~98 uppercase array constants in the codebase. The exclusions above filter out confirmed-legitimate static UI constants (tabs, options, labels, config arrays). The remaining 0 hits after filters confirms no domain-data fixtures exist.
