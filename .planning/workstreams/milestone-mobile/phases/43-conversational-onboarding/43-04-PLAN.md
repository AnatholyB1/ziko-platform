<objective>
Implement ONBOARD-06: athletes who completed the pre-v1.18 structured onboarding get a starting level
computed by the AI from their real activity history the next time they open the app — never a flat
default. Also add the live RPC/RLS spec proving the ONBOARD-05 starting-state write contract.

Purpose: this is the one path in Phase 43 where real logged data exists and therefore MUST be the
evidence (43-RESEARCH.md Pitfall 4 — explicitly distinct from the fresh-onboarding conversation path,
which legitimately uses its own extraction). It is triggered lazily by `authStore.refreshProfile()`
(plan 43-02), mirroring the established v1.4 lazy-daily-reset precedent instead of adding a cron.

Output: an activity-aggregation + inference module, the `POST /ai/onboarding/retroactive` route handler,
a unit spec, and a live RPC spec.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mobile client → POST /ai/onboarding/retroactive | An unauthenticated or cross-user call would trigger a state write for someone else |
| activity tables → model prompt | Real athlete activity aggregates cross into an LLM inference |
| module → record_athlete_decision | Retroactive path writes the same privileged state as the onboarding tool |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-43-16 | Spoofing | POST /ai/onboarding/retroactive | mitigate | Handler derives userId exclusively from `c.get('auth')` set by `authMiddleware`; no user identifier is read from the request body |
| T-43-17 | Tampering | double-write race from two refreshProfile calls per app open | mitigate | `state_exists` guard read before any model call or RPC, plus the client-side in-flight guard from plan 43-02. Residual: a true simultaneous race could write two `onboarding_profile` journal rows against one state row — accepted, since the state row is upserted once and Phase 44's engine supersedes it |
| T-43-18 | Repudiation | ungrounded retroactive decision | mitigate | `p_evidence` carries the actual queried aggregates plus `evidence_source: 'real_activity_history'`; a spec assertion pins the aggregate values into the evidence payload |
| T-43-19 | Denial of Service | model call per app open | mitigate | The `state_exists` guard makes the model call fire at most once per athlete lifetime; every subsequent app open short-circuits on a single indexed read |
| T-43-20 | Information Disclosure | activity aggregates in the prompt | accept | Only the athlete's own counts are sent, to the same Anthropic provider already used for their chat; no cross-athlete data is aggregated |
| T-43-SC | Tampering | npm/pip/cargo installs | accept | This plan installs zero packages — `zod@^4.3.6` and `ai@^6.0.116` are already in `backend/api/package.json` |
</threat_model>
