<objective>
Build `POST /ai/onboarding/stream`: the mandatory, uncredited, single-tool conversational turn that
asks Ziko's ≤4 questions in the athlete's locale and terminates by calling `assess_profile`.

Purpose: this is the only server surface the Ziko chat screen talks to. It must be exempt from
`creditCheck`/`creditDeduct` (a brand-new athlete has balance 0 against a chat cost of 4 and cannot
legally skip a mandatory flow — 43-RESEARCH.md Pitfall 2), must expose only `assess_profile`, and must
carry the athlete's locale, since no per-athlete locale exists anywhere else in the stack (Pitfall 3).

Output: a new `routes/onboarding.ts` router mounted under `/ai`, plugin_context tagging in
`context/conversation.ts`, and a route-level spec.
</objective>

    - State the terminal condition: once it has signal on all three categories, it must call

    - State that `micro_action` must be one of `hydration_log`, `journal_mood`, `measurements_weight`

    1. Parse the body as `{ messages?: Array<{role:'user'|'assistant'; content:string}>, conversation_id?: string, locale?: 'fr'|'en' }`.
       Resolve `conversation_id` from the body or the `X-Conversation-Id` header, matching the
       `/chat/stream` precedent. Normalize `locale` to `'en'` only when it is exactly `'en'`, otherwise `'fr'`.
    2. Read `userId` from `c.get('auth')` and the raw bearer token from the Authorization header.
    3. Call `getOrCreateConversation(userId, conversation_id, userToken, { type: 'ziko_onboarding', locale })`.
    4. Ownership + tag gate, before any model call: when a `conversation_id` was supplied, verify the
       returned `userId` equals the authenticated `userId` and the returned
       `pluginContext.type === 'ziko_onboarding'`. On mismatch respond `403` with
       `{ error: 'conversation_forbidden' }` and stream nothing. Without this check an athlete could
       point the onboarding turn at another athlete's chat conversation or at their own general chat.
    5. Resolve the effective locale from `pluginContext.locale` when present, falling back to the
       request's normalized locale — the conversation record is the source of truth so the locale cannot
       drift mid-conversation (43-RESEARCH.md Open Question 2 recommendation, adopted).
    6. Merge `convo.history` with the incoming `messages` exactly as `/chat/stream` does.
    7. Build a one-entry tools object: `{ assess_profile: tool({ description: assessProfileSchema.description, inputSchema: jsonSchema(assessProfileSchema.parameters), execute: (input) => assess_profile(input, userId, userToken) }) }`.
       Never call `buildSDKTools()` and never spread `allToolSchemas` — a wider surface lets the model
       burn steps on off-task tools inside the tight cap (43-RESEARCH.md Anti-Patterns).
    8. `streamText({ model: AGENT_MODEL, system: buildOnboardingSystemPrompt(effectiveLocale), messages, tools, stopWhen: [isStepCount(ONBOARDING_MAX_STEPS), hasToolCall('assess_profile')] })`.
       Import `isStepCount` and `hasToolCall` from `'ai'` alongside `streamText`, `tool`, `jsonSchema`.
    9. Set the same three SSE headers as `/chat/stream` and return `stream(c, async (s) => { ... })`
       replicating its loop: emit `meta` with the conversation id first, then `chunk` events for
       `text-delta` parts using the same XML-artifact filter, then `[DONE]`. Catch inside the callback,
       emit `{ type: 'error', error }` followed by `[DONE]`, and never let an exception escape past the
       writer.
    10. New SSE event: when a `tool-result` part arrives for `assess_profile` and its output has
        `success === true`, accumulate a mission payload and emit exactly one
        `data: {"type":"mission","mission":{"micro_action":...,"mission_title":...,"decision_id":...}}\n\n`
        before `[DONE]`. This mirrors how `/chat/stream` emits its `actions` event from the
        `app_navigate` tool result. When the tool output has `success === false`, emit
        `{ type: 'error', error: <the tool's error string> }` instead — a failed state write must never
        look like a completed onboarding.
    11. Cap failure handling: track whether an `assess_profile` tool result was ever observed. If the
        stream ends without one, emit `data: {"type":"cap_reached"}\n\n` before `[DONE]`. The client
        renders the `coach.onboarding.error.capReached` copy against this signal. Do not silently
        finish — an athlete who answered questions but has no `athlete_state` row must not be treated
        as onboarded.
    12. Persistence tail: after the stream, `appendMessages(conversationId, [...])` with the last user
        message and the accumulated assistant text, exactly as `/chat/stream` does. This is what makes
        D-04's mid-flow resume work after an app kill.
    13. Reuse the token-usage logging pattern from `routes/ai.ts` (`onFinish: ({ totalUsage }) => ...`
        inserting into `ai_cost_log`) so this uncredited call is still cost-visible. Full autonomous-call
        cost coverage is Phase 47's requirement; this is the cheap local case.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mobile client → POST /ai/onboarding/stream | Untrusted body (messages, conversation_id, locale) crosses into a privileged, uncredited AI turn |
| athlete free text → system prompt | Athlete-authored answers reach a model that can call a state-writing tool |
| route → ai_conversations / ai_messages | Conversation id from the client selects which rows are read and appended to |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-43-10 | Information Disclosure | conversation_id body/header field (IDOR) | mitigate | Ownership gate in Task 2 step 4: reject with 403 `conversation_forbidden` unless the conversation's `user_id` equals the authenticated userId AND `plugin_context.type === 'ziko_onboarding'`, before any model call or message append |
| T-43-11 | Spoofing | route authentication | mitigate | `onboardingRouter.use('*', authMiddleware)` — the router is mounted under `/ai` but carries its own auth middleware; userId is never read from the body |
| T-43-12 | Elevation of Privilege | prompt injection through athlete free-text answers | mitigate | Tool surface narrowed to `assess_profile` only; `level`/`tier` are server-side constants the model cannot set; `readiness` is enum-constrained at the schema and at the DB CHECK. Residual risk (an athlete talking themselves into `readiness: 'ready'`) is accepted — Phase 44's weekly engine is the designed correction mechanism |
| T-43-13 | Denial of Service | unbounded model turns on an uncredited route | mitigate | `stopWhen: [isStepCount(ONBOARDING_MAX_STEPS), hasToolCall('assess_profile')]` caps the turn at 8 steps; the route is only reachable by an authenticated athlete who has not yet completed onboarding |
| T-43-14 | Repudiation | uncredited AI spend | mitigate | `onFinish` logs `totalUsage` to `ai_cost_log` (Task 2 step 13) so the exempted route is still cost-attributable |
| T-43-15 | Tampering | silent cap-reached completion | mitigate | Explicit `cap_reached` SSE event when the turn ends without an `assess_profile` result; the client must not treat that stream as a completed onboarding |
| T-43-SC | Tampering | npm/pip/cargo installs | accept | This plan installs zero packages |
</threat_model>
