Ship `public.record_athlete_decision()` — the one and only write path to `athlete_state` and `athlete_decisions` — and the DB-level grant lockdown that makes that claim literally true at the Postgres layer rather than a code-review convention.

Purpose: FOUND-03 (single server-side write path), FOUND-04 (no direct client write possible), FOUND-02 (evidence mandatory). This is the phase's security core: after this migration, neither an athlete's JWT nor the backend's own `service_role` key can mutate either table except through this function.

**1. The function.** Define `public.record_athlete_decision(...)` with exactly the signature, language, `SECURITY DEFINER` marker and `SET search_path = public, pg_temp` shown in this plan's `<interfaces>` block. Body ordering, in this order:

a. Guard first, before touching any table: if `p_evidence IS NULL OR jsonb_typeof(p_evidence) <> 'object'` then return `jsonb_build_object('success', false, 'error', 'evidence_required')`. Return an error-shaped JSONB, never `RAISE EXCEPTION` — matching `grant_premium_credits`'s `invalid_amount` guard.

b. Insert the journal row into `public.athlete_decisions` with `(user_id, decision_type, week_of, summary, rationale, evidence, outcome, source)`, coalescing `p_outcome` to `'{}'::jsonb` and `p_source` to `'weekly_review_cron'`. Attach `ON CONFLICT (user_id, decision_type, week_of) WHERE decision_type = 'weekly_focus' AND week_of IS NOT NULL DO NOTHING` — the column list and predicate must match `idx_athlete_decisions_week_idempotency` character-for-character or Postgres will fail to infer the arbiter index. Use `RETURNING id INTO v_decision_id`.

c. Detect the duplicate: `GET DIAGNOSTICS v_rows = ROW_COUNT;` and if `v_rows = 0`, return `jsonb_build_object('success', false, 'error', 'duplicate')` and stop — the state patch must NOT be re-applied on an at-least-once cron retry (this is what makes ENGINE-04's idempotency guarantee real).

d. Self-heal the parent row: `INSERT INTO public.athlete_state (user_id) VALUES (p_user_id) ON CONFLICT (user_id) DO NOTHING;` so the first-ever decision for an athlete (Phase 43 onboarding) creates the row with schema defaults before patching it.

e. Patch the state row with a single `UPDATE public.athlete_state ... WHERE user_id = p_user_id`, applying `COALESCE(p_state_patch->>'<key>', <column>)` semantics per recognised key listed in `<interfaces>`, with these three deliberate exceptions:
   - `points` and `tier` use a monotonic ratchet: `points = GREATEST(points, COALESCE((p_state_patch->>'points')::int, points))` and the same shape for `tier`. Rationale (put it in a code comment): REWARD-04 requires unlocked tiers/points to never be revoked or decreased, and this RPC is the only place that invariant can be enforced at the DB layer.
   - `level` uses a plain `COALESCE` with NO `GREATEST` guard. Rationale (put it in a code comment): ENGINE-03 explicitly requires the Phase 44 weekly engine to be able to de-escalate as well as escalate, so `level` must remain freely settable; the `level >= 1` CHECK on the column is the floor.
   - `last_review_at` and `next_review_due_at` are only advanced for weekly reviews: `last_review_at = CASE WHEN p_decision_type = 'weekly_focus' THEN NOW() ELSE last_review_at END`, and `next_review_due_at = CASE WHEN p_decision_type = 'weekly_focus' THEN NOW() + INTERVAL '7 days' ELSE next_review_due_at END`. Rationale (code comment): an onboarding or reward-grant decision must not silently reset the weekly review clock.
   Also set `updated_at = NOW()` (belt-and-braces alongside the `trg_athlete_state_updated` trigger).
   For the JSONB-valued keys (`current_focus_detail`, `onboarding_profile`), use `COALESCE(p_state_patch->'<key>', <column>)` (the `->` arrow, not `->>`).

f. Return `jsonb_build_object('success', true, 'decision_id', v_decision_id)`.

Add `COMMENT ON FUNCTION public.record_athlete_decision(UUID, TEXT, DATE, TEXT, TEXT, JSONB, JSONB, TEXT, JSONB)` documenting for Phase 43+: that `p_state_patch` accepts any subset of the recognised keys so callers never need this migration touched again; that the first call for a new athlete self-creates the `athlete_state` row with defaults (`readiness='fragile'`, `level=1`, `tier=1`, `points=0`, `status='onboarding'`); that `points`/`tier` are ratcheted and cannot be decreased; and that `p_evidence` must carry the real activity data the decision was based on, which the schema can require but not validate.

**2. Function EXECUTE lockdown.** Immediately after the function, and naming every role explicitly (a bare `REVOKE ... FROM PUBLIC` is proven insufficient on this project because `ALTER DEFAULT PRIVILEGES` materialises per-role grants at `CREATE FUNCTION` time):
`REVOKE EXECUTE ON FUNCTION public.record_athlete_decision(UUID, TEXT, DATE, TEXT, TEXT, JSONB, JSONB, TEXT, JSONB) FROM PUBLIC, anon, authenticated;`
`GRANT EXECUTE ON FUNCTION public.record_athlete_decision(UUID, TEXT, DATE, TEXT, TEXT, JSONB, JSONB, TEXT, JSONB) TO service_role;`

**3. Table write lockdown (D-06/D-07).** Under a "Lock down every direct write path" comment noting that `SECURITY DEFINER` functions run as the function owner and are therefore unaffected by these revocations:
`REVOKE INSERT, UPDATE, DELETE ON public.athlete_state FROM authenticated, service_role;`
`REVOKE INSERT, UPDATE, DELETE ON public.athlete_decisions FROM authenticated, service_role;`
D-06 names `UPDATE` on `athlete_state` and `INSERT` on `athlete_decisions` as the required minimum; this migration revokes all three write verbs on both tables because D-06's stated purpose is that `record_athlete_decision()` be "the only code path capable of writing either table" and D-07 forbids any carve-out. Add a comment recording that widening. Do NOT revoke `SELECT` — the RLS SELECT policies from plan 42-01 are the read-scoping layer and must keep working, and `service_role` needs SELECT for Phase 46's gating reader and Phase 47's context query. Do NOT name the migration-runner/table-owner role (typically `postgres`) in any REVOKE — that would break the `SECURITY DEFINER` function itself.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Athlete JWT (`authenticated`) → PostgREST → `athlete_state` / `athlete_decisions` | Athlete could otherwise set their own `level`/`readiness`/`tier` (which gate plugin access in Phase 46) with a single SDK call. |
| Backend `service_role` key → PostgREST/Postgres | `BYPASSRLS` makes RLS irrelevant here. Includes the "engineer writes a quick-fix script with the service key" and "leaked env var" cases. |
| Future tool executor (Phase 43-45) → `record_athlete_decision()` | The executor supplies `p_evidence`; the DB can require its presence but cannot verify its truthfulness. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-01 | Elevation of Privilege | `athlete_state` direct write by an authenticated athlete | mitigate | `REVOKE INSERT, UPDATE, DELETE ON public.athlete_state FROM authenticated` plus the zero-write-policy RLS from plan 42-01 — two independent layers. Verified by the authenticated-write-blocked assertion in plan 42-03. |
| T-42-02 | Tampering | `service_role` key used outside the intended code path to write either table | mitigate | `REVOKE INSERT, UPDATE, DELETE ... FROM service_role` on both tables. `BYPASSRLS` and table GRANTs are independent Postgres subsystems, so the revoke is effective against `service_role` (42-RESEARCH.md §Pitfall 2). This is the phase's load-bearing new control — no prior migration in this repo revokes from `service_role`. Verified by the admin-write-blocked assertions in plan 42-03. |
| T-42-05 | Elevation of Privilege | `anon`/`authenticated` calling `record_athlete_decision()` directly to write arbitrary state for any `p_user_id` | mitigate | `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` naming each role explicitly — a `PUBLIC`-only revoke leaves the per-role grants materialised by this project's `ALTER DEFAULT PRIVILEGES` intact. `EXECUTE` granted solely to `service_role`. Verified by the anon-and-authenticated-RPC-denied assertions in plan 42-03. |
| T-42-06 | Tampering | At-least-once cron retry double-applying a weekly state patch (points/tier inflation) | mitigate | Partial unique index arbiter + `GET DIAGNOSTICS ROW_COUNT = 0` early return before the `UPDATE`, so a duplicate is a true no-op rather than a re-patch. Verified by the idempotency assertion in plan 42-03. |
| T-42-07 | Tampering | A buggy caller decreasing an already-unlocked `points`/`tier` (implicit punishment, REWARD-04 violation) | mitigate | `GREATEST(current, incoming)` ratchet on `points` and `tier` inside the RPC — the only DB-layer place this invariant can be enforced. `level` is intentionally exempt because ENGINE-03 requires de-escalation. |
| T-42-03 | Repudiation | Decision recorded with fabricated or empty `p_evidence` | accept (partial mitigation) | Schema + RPC guard enforce presence and object-shape only. Truthfulness is out of Phase 42's reach (no caller exists); documented in the `COMMENT ON FUNCTION` as a Phase 43+ tool-executor code-review obligation, per 42-RESEARCH.md §Architectural Responsibility Map. |
| T-42-08 | Denial of Service | Over-broad REVOKE breaking the `SECURITY DEFINER` owner or the RLS read path | mitigate | REVOKE lists name only `authenticated` and `service_role` (never the migration-runner/table-owner role), and `SELECT` is never revoked. Asserted negatively in Task 1's verify command; smoke-tested end-to-end by the admin-RPC-succeeds assertion in plan 42-03. |
| T-42-SC | Tampering | npm/pip/cargo installs | accept | Zero package installs in this phase — pure Postgres DDL (42-RESEARCH.md §Package Legitimacy Audit). No slopcheck gate required. |
