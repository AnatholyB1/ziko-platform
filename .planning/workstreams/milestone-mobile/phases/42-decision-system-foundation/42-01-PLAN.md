Table `public.athlete_state` (PK = user_id, one row per athlete):
  user_id UUID PK -> auth.users(id) ON DELETE CASCADE
  status TEXT NOT NULL DEFAULT 'onboarding'  CHECK IN ('onboarding','active','paused')
  readiness TEXT NOT NULL DEFAULT 'fragile'  CHECK IN ('fragile','building','ready')   -- D-01/D-02
  level INTEGER NOT NULL DEFAULT 1  CHECK (level >= 1)
  points INTEGER NOT NULL DEFAULT 0  CHECK (points >= 0)
  tier INTEGER NOT NULL DEFAULT 1  CHECK (tier >= 1)
  onboarding_profile JSONB NOT NULL DEFAULT '{}'
  current_focus_summary TEXT
  current_focus_detail JSONB NOT NULL DEFAULT '{}'
  rolling_summary TEXT
  last_review_at TIMESTAMPTZ
  next_review_due_at TIMESTAMPTZ
  created_at / updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
  -- NO `track` column (D-03)

Table `public.athlete_decisions` (append-only):
  id UUID PK DEFAULT gen_random_uuid()
  user_id UUID NOT NULL -> auth.users(id) ON DELETE CASCADE
  decision_type TEXT NOT NULL CHECK IN ('onboarding_profile','weekly_focus','level_change','reward_grant','program_created','goal_created')
  week_of DATE
  summary TEXT NOT NULL
  rationale TEXT
  evidence JSONB NOT NULL CHECK (jsonb_typeof(evidence) = 'object')
  outcome JSONB NOT NULL DEFAULT '{}'
  source TEXT NOT NULL DEFAULT 'weekly_review_cron' CHECK IN ('weekly_review_cron','onboarding_tool','app_open_fallback','manual_admin')
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

Already-shipped function reused (do NOT redefine): public.handle_updated_at()
  — defined in supabase/migrations/001_initial_schema.sql

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Mobile/web client (`anon`/`authenticated` JWT) → Postgres via PostgREST | Untrusted athlete-controlled input reaches the tables directly through the Supabase SDK; RLS is the only row-scoping layer at this boundary. |
| Backend Hono code (`service_role` key) → Postgres | Trusted-but-fallible: `service_role` carries `BYPASSRLS`, so RLS provides zero protection here. Grant-level control is the only lever (applied in plan 42-02). |
| Postgres role-default privileges → any newly created object | This project's `ALTER DEFAULT PRIVILEGES` auto-grants CRUD/EXECUTE to `anon`/`authenticated`/`service_role` at object-creation time — a new object is NOT locked down by default. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-01 | Elevation of Privilege | `athlete_state` (`level`, `readiness`, `tier` drive Phase 46 plugin gating) | mitigate | RLS enabled with a single `FOR SELECT` policy and zero write policies — the explicit `FOR SELECT` command restriction is asserted in Task 1's acceptance criteria (an unrestricted `USING/WITH CHECK` policy, as in `026_ai_credits.sql`, would re-open writes). Grant-level lockdown for `service_role` is completed in plan 42-02. |
| T-42-02 | Information Disclosure | `athlete_state` / `athlete_decisions` cross-athlete read | mitigate | `USING ((SELECT auth.uid()) = user_id)` on both SELECT policies; `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` asserted on both tables. Verified by the cross-read-denied assertions in plan 42-03. |
| T-42-03 | Repudiation | `athlete_decisions.evidence` | mitigate (partial) | `evidence JSONB NOT NULL CHECK (jsonb_typeof(evidence) = 'object')` makes an ungrounded decision unwritable at the schema layer. The schema can enforce presence, not truthfulness — verifying evidence reflects a real activity query is documented as a Phase 43+ tool-executor obligation in the column comment. |
| T-42-04 | Information Disclosure / EoP | New objects inheriting project default privileges | mitigate | This plan deliberately emits zero GRANT/REVOKE statements and defers all lockdown to plan 42-02's single consolidated migration, so no partially-locked window can be introduced by statement ordering across files. Plan 42-02 names every role explicitly (`PUBLIC, anon, authenticated`, `authenticated, service_role`) — a bare `REVOKE ... FROM PUBLIC` is proven insufficient on this project. |
| T-42-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this phase — pure Postgres DDL, zero new dependencies (confirmed in 42-RESEARCH.md §Package Legitimacy Audit). No slopcheck gate required. |
