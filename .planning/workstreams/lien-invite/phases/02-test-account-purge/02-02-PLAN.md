<objective>
Build the safety net that has to exist before anything is deleted: an unconditional export of the
exact rows about to disappear, and a real reading of whether the project has point-in-time recovery
to fall back on.

Purpose: D-04 makes the row export the primary, unconditional mechanism precisely because it
restores just the affected rows fast, where PITR is a project-wide, slower, more disruptive recovery.
`research/PITFALLS.md` Pitfall 13 step 3 puts a fresh export immediately before the deletion, and
notes that "restore this row from a CSV I exported 5 minutes ago" is a different class of recovery
from a full PITR rewind.

Output: `scripts/purge-test-accounts/export.mjs` and `pitr.mjs`, plus the `export-<ISO>.manifest.json`
contract that plan 02-03's delete step refuses to run without.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → Supabase Management API | `SUPABASE_ACCESS_TOKEN` is an account-scoped credential, broader than the project service-role key |
| operator shell → Supabase Auth + PostgREST | The service-role key reads `user_profiles` and the deny-all `waitlist_signups` table |
| exported rows → local filesystem | The export file is a plaintext copy of real personal data, held outside the database's RLS entirely |
| manifest → the delete step | The manifest is the authorization token for an irreversible action; whoever can edit it can widen the delete set |
