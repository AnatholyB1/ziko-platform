# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase shape reminder:** this is a content-and-small-code phase, not a component-build phase (per `03-RESEARCH.md` Summary). Two real page routes ship (new CGV, revised CGU consistency fix), both FR+EN, plus copy-only deliverables for Phase 5's consent checkbox/notice. The counsel-briefing package (D-02) is a plain Markdown document under `.planning/workstreams/lien-invite/phases/03-legal-cgv-cgu/03-COUNSEL-BRIEFING.md` — it is **not** a live page and has **no visual/UI form at all**; this UI-SPEC governs only the rendered `apps/web` surfaces (CGV page, CGU revision, draft-pending banner, footer link).

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — plain HTML elements + Tailwind v4 utility classes (`@theme` tokens in `apps/web/src/app/globals.css`) |

**shadcn gate decision (assumption, documented per auto-mode):** `components.json` was not found anywhere in `apps/web`, and none of the three existing legal pages (`cgu`, `mentions-legales`, `politique-de-confidentialite`) use a component library — they are plain Tailwind-classed JSX. Initializing shadcn now, for a content-only legal-drafting phase with a single new stateless banner element, would introduce an inconsistency with the three pages this phase must match stylistically. Declined; `Tool: none` is the correct call for this phase's scope. If a future UI phase (e.g. Phase 5's waitlist form) needs real form components, shadcn should be evaluated there instead.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (`text-base`, implicit) | 400 (regular) | 1.625 (`leading-relaxed`) |
| Label | 14px (`text-sm`) | 400 (regular) | 1.5 |
| Heading | 20px (`text-xl`) | 600 (semibold) | 1.3 |
| Display | 30px (`text-3xl`) | 600 (semibold) | 1.2 |

**Two weights declared: 400 (regular) and 600 (semibold).** This is a deliberate simplification of the existing precedent, which uses three weights across the CGU/mentions-légales/politique pages (`font-bold` 700 on `<h1>`, `font-semibold` 600 on `<h2>`, `font-bold` 700 again on the medical-disclaimer banner headline). For this phase's **new** surfaces — the CGV page's `<h1>`/`<h2>`, and the new draft-pending-review banner headline on both CGV and CGU — use `font-semibold` (600) uniformly at the sizes above, never `font-bold` (700). Untouched existing `<h1>` elements on `cgu`/`mentions-legales`/`politique-de-confidentialite` keep their current `font-bold` — retrofitting them is out of this phase's scope; only sections actually revised for LEGAL-04 consistency should adopt the 600-weight contract if their heading is touched.

Role mapping for this phase's concrete elements:
- Display (30px/600): CGV `<h1>`, CGU `<h1>` (only if touched)
- Heading (20px/600): CGV `<h2>` section titles, CGU `<h2>` sections revised for LEGAL-04, **and** the draft-pending-review banner headline (previously 18px/`text-lg` in the CGU's medical-disclaimer precedent — standardized up to 20px/Heading role for this phase's new banner, one fewer special case)
- Body (16px/400): all paragraph prose, list items, banner body text
- Label (14px/400): "Dernière mise à jour" footer line, any inline meta text

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F7F6F3` (`--color-background`) | Page canvas — applied globally at `<body>` (`apps/web/src/app/[locale]/layout.tsx:36`), not re-declared per-page |
| Secondary (30%) | `#FFFFFF` (surface, implicit — no explicit `bg-white` container on these pages) | Not actively used as a card/panel background on this phase's pages — legal prose sits directly on the background canvas with no card containers; reserved role, present for contract completeness only |
| Accent (10%) | `#FF5C1A` (`--color-primary`) | Reserved for: (1) cross-document links between legal pages (`text-primary underline`, e.g. CGU → Politique de confidentialité, CGV → CGU) — exact existing pattern, unchanged; (2) footer nav link hover state (existing `AnimatedLink` treatment) |
| Destructive | not applicable | This phase has no destructive UI action. The erasure mechanism (LEGAL-09/D-06) is a human-operated backend script/RPC invocation (`anonymize_waitlist_signup()`), never a UI control — see `03-RESEARCH.md` Pattern 5. No "delete" button exists on any page this phase ships. |

**Draft-pending-review banner — explicit deviation from the cited precedent, and why.** `03-RESEARCH.md` Pattern 3 cites the CGU's existing medical-disclaimer box (`border-2 border-primary bg-orange-50`) as the structural template. That box overloads `--color-primary` (the brand accent, reserved above for links/CTAs) as a warning-box border, and `bg-orange-50` is an arbitrary Tailwind stock color never declared in `globals.css`'s `@theme` block. `globals.css` already declares real semantic warning tokens that this precedent never uses: `--color-warning: #F59E0B` and `--color-warning-subtle: #FFFBEB`. For the **new** draft-pending-review banner (this phase's own discretion call per CONTEXT.md), use those semantic tokens instead:

```
border-2 border-warning bg-warning-subtle
```

with the `IoWarningOutline` icon and headline text in `text-warning`, body text in `text-text` (unchanged). This keeps `--color-primary` reserved for actual brand/interactive elements and uses tokens that already exist in the design system but were previously unused. The existing medical-disclaimer box (out of this phase's scope) is left as-is — do not retrofit it.

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5). Only two element kinds are actually rendered by this phase: `static-content` (CGV page body, revised CGU sections, the draft-pending banner) and `nav` (the new footer CGV link). The consent-checkbox/collection-notice copy is explicitly **not** classified here — per D-07 the checkbox/notice UI itself does not render this phase (Phase 5's job); its state coverage belongs in Phase 5's own UI-SPEC, not this one.

Applicable state considerations resolved: 4 covered, 0 backstop, 0 unresolved (2 dismissed as not applicable to this phase's element kinds).

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| overflow | CGV/CGU static-content prose | ✅ covered | Legal prose renders in a naturally-flowing `<section>`/`<p>` stack with no fixed-height or `overflow:hidden` container — length never gets clipped, matches existing `cgu`/`mentions-legales`/`politique-de-confidentialite` precedent verbatim. |
| long-text | CGV/CGU static-content prose | ✅ covered | Body paragraphs wrap naturally via `leading-relaxed` with no truncation/ellipsis; section headings and the banner headline are short, fixed strings in both locales, never dynamically long or user-generated. |
| overflow | Footer CGV nav link | ✅ covered | `"CGV"`/`"Terms of Sale"` is the same length class as the existing `"CGU"`/`"Terms of use"` label already proven to fit `FooterClient.tsx`'s `flex flex-wrap` nav row — no special-casing needed. |
| long-text | Footer CGV nav link | dismissed | Nav label is a fixed short string in both locales, not user-generated or dynamic-length content. |
| loading | Footer CGV nav link | dismissed | Static Next.js `<Link>`, SSR-rendered — no client-side loading/async state exists for internal navigation links in this codebase. |
| error | Footer CGV nav link | dismissed | Static internal navigation link with no runtime failure mode; a broken route is a build-time/lint error, not a UI state to design for. |

Categories not raised at all (not applicable to any element kind in this phase): `empty`, `populated`, `partial`, `zero-one-many` — all require a `form`, `list-collection`, or `media` element, none of which render in this phase (the waitlist form and counter belong to Phase 5).

**Draft-pending-review banner lifecycle note (outside the closed taxonomy, prose-owned):** the banner has exactly two lifecycle states — present (draft, pre-counsel-approval) and absent (removed once D-01's checkpoint clears). This is a one-time manual removal task tied to the checkpoint's resolution, not a runtime UI state; `03-RESEARCH.md`'s Security Domain section already flags "banner forgotten after approval" as a follow-up risk to track, not something this UI-SPEC can encode as a rendered state.
