## Resolved at plan time: does `creditGate.ts` still need to read `tier`?

04-RESEARCH.md left this open ("Open Questions" 1). Resolved here, no checkpoint — it is an
implementation-shape choice, not a one-way door.

**Answer: the enforcing path reads no `tier` at all; the legacy path must keep reading it.**

Once the cap is enabled, premium and free users are distinguished only by balance size, and balance
checking is already tier-agnostic — so the `.select('tier')` query is genuinely dead on that path
and is removed from it. But the flag-off path exists precisely to reproduce *today's* behavior at
deploy time, and today's behavior is tier-specific: premium bypasses, free does not. A flag-only
pass-through (the shape both 04-RESEARCH.md Pattern 3 and 04-PATTERNS.md draft) would make every
free user bypass the gate while the flag is off, which is the shipped default. That is a far worse
regression than the one this phase is fixing.

So: read the flag first (a one-row primary-key lookup); on flag-true do the tier-free path; on
flag-false run the legacy branch, tier read included. Net query count on the target path is
unchanged (one flag read replaces one tier read). The legacy branch becomes dead code the instant
Phase 6 flips the flag, and deleting it later is a one-line change that leaves `creditGate.ts` with
zero `tier` reads — which is the end state the research was reaching for.
