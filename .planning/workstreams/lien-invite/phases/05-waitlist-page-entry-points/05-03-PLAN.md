<objective>
Give the founders page the one number it is allowed to show, and make that number honest: fetched
live from the database on every view, revealed only when the database says so, never increasing in
front of a visitor, and replaced by a real completion state rather than a zero once all two hundred
spots are gone.

Purpose: this is the requirement cluster the whole milestone was designed around. `REQUIREMENTS.md`
rules out inflated, offset and simulated counters explicitly, on the grounds that a fabricated
scarcity figure is a misleading commercial practice. Phase 1 already put every one of those
guarantees inside a single SQL function whose output is three booleans and an integer. The only way
to break them now is to compute something in the frontend, so this plan's discipline is almost
entirely about what it refuses to calculate.

Output: a public counter route backed by the service-role admin client, one self-contained client
widget with three mutually exclusive states plus a loading and a failure state, mounted into the
founders hero, and two suites that pin the contract at both ends.
</objective>

## Resolved at plan time — how this response is actually cached

`05-RESEARCH.md` Pattern 3 and `05-PATTERNS.md` both draft the route with `export const revalidate =
30` and the browser calling it as `fetch('/api/waitlist/count', { next: { revalidate: 30 } })`.
Neither does what it looks like, and both are replaced here.

The `next` option on `fetch` is a server-side extension. In a browser it is an unrecognised property
on the request init object and is silently ignored, so the drafted client call has no caching
behaviour at all. And a `revalidate` export on a GET route handler asks Next to evaluate the handler
at build time and serve it as a static asset — which would call `createAdminClient()` during
`next build`, in an environment that may hold no service-role credentials, turning a missing
environment variable into a failed build rather than a degraded counter.

So: the route exports no caching symbols and instead sets an explicit `Cache-Control` of
`public, s-maxage=30, stale-while-revalidate=60` on its success response, which is what genuinely
caches it at the edge for thirty seconds; the fallback response sets `no-store` so a transient
upstream failure cannot be held for the whole window; and the client calls it with a plain `fetch`
and no init options, letting the response's own headers govern.

This changes nothing about the requirements: FOND-03 asks that the number come from a real query, and
a thirty-second edge cache over a real query is still a real query — the same thirty seconds the
research intended, just enforced by the mechanism that actually enforces it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous internet → `/api/waitlist/count` | A public, unauthenticated, uncredentialled GET that anyone may call at any rate. |
| Route Handler → `get_waitlist_founder_status()` (service role) | The route holds the service-role key. Whatever it asks for, it gets, unconstrained by RLS. |
| Route Handler response → CDN → every visitor | One cached response is served to everyone for its lifetime, so anything visitor-specific or wrong in it is wrong at scale. |
| database verdict → rendered marketing claim | The number on the page is a commercial representation. A frontend that recomputes it is a frontend that can misrepresent it. |
