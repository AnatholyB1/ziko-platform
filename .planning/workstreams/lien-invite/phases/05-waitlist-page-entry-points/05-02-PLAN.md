## Resolved at plan time — four decisions this plan makes explicitly

**1. The consent write runs on every successful submission, new or duplicate, and it runs before the
non-disclosure branch.** `05-RESEARCH.md` Open Question 2 left this open and Assumption A1 recommended
the unconditional form on evidentiary grounds. There is a second, stronger reason: DATA-07's whole
guarantee is that the new and duplicate paths are indistinguishable from outside. Gating the write on
`is_new` would give the duplicate path strictly less work to do, which is a timing difference an
attacker can measure. Running it unconditionally, ahead of the branch, keeps both paths structurally
identical — the security argument and the evidentiary argument point the same way.

**2. The consent write matches on `email_normalized`, resolved by calling the database's own
`normalize_waitlist_email` RPC.** `05-RESEARCH.md` Pattern 2 drafts a match on the `email` column
using a client-side lowercase-and-trim. That misses every case the normalizer exists for: a duplicate
submitted as `test.user+promo@gmail.com` maps to a row whose stored `email` is the *original*
submitter's spelling, so the update silently writes zero rows and the consent columns stay null with
no error. Calling the RPC costs one round trip and is the same discipline Phase 3's erasure script
recorded — never re-implement the normalizer outside SQL.

**3. Consent is required server-side, not merely gated client-side.** The collection notice names
consent as the legal basis for the entire processing, so a row written without it is a row that
should not exist. The action refuses the submission when the consent field is absent. This is why the
existing concurrency suite's form fixtures gain a consent field in T-05-05 — a fixture change that
adds a field the production form always sends, leaving every assertion in that suite untouched.

**4. ENTRY-06 is satisfied server-side by the UTM columns Phase 1 already ships, and Plan 05-05 adds
the client-side event on top.** `claim_waitlist_signup` already accepts `p_utm_source` and
`p_utm_campaign`; the shipped action simply never passes them. Wiring them costs two hidden inputs
and two arguments, survives ad-blockers, needs no vendor, and makes conversions answerable by direct
SQL. It is the durable half of ENTRY-06 and it lands here.

## Guard order

Fixed by `05-RESEARCH.md`'s architecture diagram and not reordered here. Honeypot, then `checkBotId`,
then the rate limit, then syntax validation, then the disposable-domain check, then the RPC. The two
local string checks sit *after* the rate limit deliberately: a flood of malformed submissions must
consume the attacker's rate-limit budget, not slip past it for free.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous internet → `claimWaitlistSpot` | The product's first unauthenticated write path. Every input is attacker-controlled and every accepted submission consumes a finite founder rank. |
| Server Action → `claim_waitlist_signup` (service role) | The action holds the service-role key and the RPC is granted to that role alone. Everything the action fails to reject reaches a `SECURITY DEFINER` function. |
| Server Action → `waitlist_signups` direct update | The one place this milestone writes the table outside an RPC. Deny-all RLS does not constrain the service role, so the filter and the column set are the entire control. |
| npm registry → `apps/web` build | Two new packages enter a code path that handles untrusted input and runs with the service-role key in scope. |
| visitor's query string → stored UTM columns | Attacker-controlled strings that will later be read by whoever queries conversions. |
