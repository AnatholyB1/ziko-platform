<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Android app binary → Google identity servers | Google decides whether the calling app is genuinely `com.ziko.mobile` using only the package name + signing-certificate SHA-1; a wrong or over-broad fingerprint is the whole attack surface here |
| Google Cloud Console → this repo | Client IDs cross into committed source (safe); the Web client Secret must not cross at all |
| Local working tree → EAS build | `google-services.json` travels as an encrypted EAS file secret, never through git |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-05 | Spoofing | Android OAuth client ↔ app identity binding | mitigate | Register the SHA-1 read from `npx eas-cli@latest credentials` for the production/preview keystore — the fingerprint that actually signs shipped builds. Task 1 acceptance criteria assert the fingerprint format and explicitly reject `apps/mobile/android/app/debug.keystore`'s fingerprint, whose private key is committed to this repo and would let any holder of it impersonate the app to Google. |
| T-01-06 | Information Disclosure | Google Web client Secret | mitigate | The secret is never pasted into the conversation, never written to `app.json`, and never stored in the repo — it is carried by the human directly to the Supabase dashboard in plan 01-03. Task 2 acceptance criteria include a repo-wide `GOCSPX` grep as a leak tripwire. |
| T-01-07 | Information Disclosure | Client IDs committed to `apps/mobile/app.json` | accept | OAuth client IDs are public-by-design and are already extractable from any shipped app binary (RESEARCH Security Domain). Committing them buys reproducible builds at no confidentiality cost. |
| T-01-08 | Spoofing | `webClientId` misconfiguration | mitigate | Passing the Android client ID where the Web client ID belongs breaks audience verification silently (RESEARCH Pitfall 3). Task 2 stores only `webClientId`/`iosClientId` and asserts they differ from each other; the Android ID is deliberately never written into app-readable config. |
| T-01-04 | Spoofing | ID token replay via disabled nonce verification | accept (pending Task 3) | Nonce verification is Supabase's default replay protection. If Task 3 returns `NONCE_UNSUPPORTED`, plan 01-03 disables it for the Google provider only — an accepted, documented risk bounded by the fact that Google ID tokens are short-lived, audience-bound to these client IDs, and delivered over TLS to the app that requested them. If Task 3 returns `NONCE_SUPPORTED`, this threat is downgraded to `mitigate` and nonce checking stays on. |
| T-01-09 | Tampering | `google-services.json` EAS file secret refresh | mitigate | When the OAuth clients live in the Firebase-backed project, the regenerated file must come from that same Firebase project's console (Sender ID unchanged) and be re-uploaded via `eas secret:create --type file`; it is never committed (`apps/mobile/.gitignore` line "google-services.json"). |
</threat_model>
