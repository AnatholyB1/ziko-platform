<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local git state → EAS cloud builders | EAS builds from the pushed/committed tree; an uncommitted config means the built binary does not match what was reviewed |
| EAS-managed credentials → signed artifacts | The release keystore and iOS signing identity live with EAS, and are the identity Google and Apple bind their trust to |
| Signed APK → physical test device | Sideloading a build outside a store channel |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-16 | Spoofing | Android build signed by the wrong keystore | mitigate | Task 2's `ANDROID_SIGNED_WITH` must read `release-keystore`. A build signed by `apps/mobile/android/app/debug.keystore` — whose private key is committed to this repo — would not match the SHA-1 registered in plan 01-02, and any later "it works" observation from such a build would be false assurance about production. |
| T-01-17 | Tampering | Building from a stale or uncommitted tree | mitigate | Task 1 records `BUILD_COMMIT` and its acceptance criteria require verifying that commit actually contains plans 01-01/01-02's `app.json` changes, so a green entitlement check cannot come from an unrelated older build (RESEARCH Pitfall 4). |
| T-01-18 | Elevation of Privilege | iOS entitlement not backed by the App ID capability | mitigate | Apple's signing step rejects a binary declaring an entitlement its App ID lacks, so `IOS_BUILD_STATUS = finished` plus the log hit on `com.apple.developer.applesignin` jointly prove the plan 01-03 capability took effect. Task 1 explicitly routes a signing failure back to plan 01-03 rather than to a workaround. |
| T-01-19 | Information Disclosure | Build logs pasted into planning documents | mitigate | Only the specific quoted line about the committed `android/` directory and boolean answers are recorded. Do not paste full build logs into the SUMMARY — EAS logs can contain environment variable names and credential identifiers. |
| T-01-20 | Tampering | Sideloaded APK on the test device | accept | The APK comes from Ziko's own EAS build page over TLS and is signed by the EAS-managed release keystore; enabling unknown-sources installation on a developer test device is standard practice and is reverted by the tester at will. |
</threat_model>
