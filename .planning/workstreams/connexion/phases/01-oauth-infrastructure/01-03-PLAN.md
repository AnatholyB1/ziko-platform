<objective>
Enable Sign In with Apple on the `com.ziko.mobile` App ID, then turn on and correctly configure the Google and Apple providers in the Supabase Auth dashboard for project `slkobhavpwsubnsmuhya`.

Purpose: OAUTH-10 (and the Apple-portal half of OAUTH-08 — a declared entitlement without a matching App ID capability fails at signing). After this plan, `supabase.auth.signInWithIdToken({ provider, token })` has a server-side counterpart that will accept tokens minted for Ziko's client IDs. This closes the last dashboard dependency before Phase 2 can write any sign-in code.
Output: Both providers live and verified via the public `/auth/v1/settings` endpoint; the Apple App ID capability enabled; a written record of the deliberate nonce trade-off.

**Scope correction the executor must surface at Task 1** — CONTEXT.md D-03 describes this checkpoint as
"Apple Developer Services ID + Sign in with Apple Key". RESEARCH.md Pitfall 8 established that wording
describes the **web OAuth** configuration path. This phase uses the native path
(`expo-apple-authentication` → `signInWithIdToken`), which per Supabase's official docs needs neither a
Services ID, nor a signing Key/.p8, nor the 6-month secret rotation — only the App ID capability. Web
Apple login is OAUTH-12, explicitly v2. Task 1 must state this correction to the user before they start
clicking, because D-03 promised them a larger set of steps than they actually need.

**Scope boundary the executor must respect** — OAUTH-10's phrasing ("le linking automatique ... est
activé") implies a toggle. RESEARCH.md Finding 1 / Pitfall 7 established there is none: automatic
linking by verified email is default, always-on GoTrue behavior. This plan therefore does NOT hunt for
that setting. The behavioral proof that linking works requires performing a real Google/Apple sign-in,
which requires Phase 2's sign-in code to exist — see the `<deferred_verification>` block below.

<deferred_verification>
## OAUTH-10's linking behavior cannot be proven in Phase 1 — deliberately, not by omission

RESEARCH.md's Validation Architecture and VALIDATION.md both specify the acceptance test for the
linking half of OAUTH-10 as: *sign up with a disposable email via email/password, then sign in with a
Google or Apple account sharing that exact verified email, and confirm one linked user (two identities)
results instead of two users.*

That test requires performing a real Google/Apple sign-in from the app. The app has no working
Google/Apple sign-in until Phase 2 wires `welcome.tsx` — this phase deliberately writes no sign-in code
(ROADMAP Phase 1 vs Phase 2 split). This is a dependency conflict, not a difficulty judgement and not a
scope reduction: there is no ID token to exchange until Phase 2 ships.

What Phase 1 therefore delivers for OAUTH-10:
- both providers enabled with correct audience configuration (Task 2), independently verified (Task 3)
- "Allow manual linking" confirmed OFF, so nothing in this phase alters the default linking semantics
- the recorded fact that automatic linking needs no activation (RESEARCH Finding 1 / Pitfall 7)

What must be carried into Phase 2's verification, and must not be dropped:
- the live disposable-account linking test above, run against production per D-05 (no staging project
  exists), using a throwaway account and never real user data

The executor must restate this carry-over item verbatim in `01-03-SUMMARY.md` so `/gsd:verify-work`
does not score OAUTH-10 as fully proven at the Phase 1 gate.
</deferred_verification>
