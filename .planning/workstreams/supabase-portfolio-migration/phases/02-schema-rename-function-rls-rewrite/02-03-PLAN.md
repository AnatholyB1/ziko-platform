<objective>
Dump ziko's live public schema and rewrite it, table/function/type name by name via the Plan 01 rename map, into a new two-file migration series under `supabase/migrations/` — schema+RLS first, functions+triggers+grants second — that creates every ziko object under a `ziko_` prefix with zero unprefixed references and zero semantic drift from the source.

Purpose: this is the actual SCHEMA-01/02/03 deliverable. RESEARCH.md verified against three real ziko function bodies that a post-hoc `ALTER TABLE RENAME` cannot rewrite identifiers embedded inside `$$...$$` function bodies or `GRANT`/`REVOKE ON FUNCTION` statements — this plan implements the two-pass approach (structural rewrite for `CREATE TABLE`/`CREATE POLICY`/`CREATE TRIGGER`, regex rewrite scoped to function bodies and grant/revoke lines) that both passes must draw from the identical rename map.
Output: `scripts/portfolio-migration/02-dump-and-rewrite.js` plus the two generated, committed migration files.
</objective>

Rewrite rule (from RESEARCH.md Pattern 2, applied uniformly): for every `old -> new` pair in the rename map, replace `\bpublic\.<old>\b` and bare `\b<old>\b` occurrences — but only where the bare form is immediately preceded by one of `FROM|JOIN|INTO|UPDATE|TABLE|REFERENCES|ON FUNCTION|FUNCTION` (case-insensitive) or appears as the `CREATE (OR REPLACE) FUNCTION`/`CREATE TABLE`/`CREATE POLICY ... ON`/`CREATE TRIGGER ... ON` target — to avoid renaming an unrelated identifier that happens to share a substring (e.g. never rewrite `coach_user_profiles_view` when renaming `user_profiles`, per RESEARCH.md's explicit non-example).
