# Stack Research

**Domain:** Cross-project Supabase migration (schema + data + RLS + RPC + auth.users + Storage) into an existing, populated, multi-tenant Supabase project
**Researched:** 2026-09-21
**Confidence:** HIGH for CLI/pg_dump/Management API mechanics (verified against current official docs and CLI); HIGH for `id` preservation in Admin API `createUser` (verified against `auth-js` TS source and the live GoTrue Go server handler, not just docs); MEDIUM for the recommended auth-merge strategy itself (synthesized from official guidance + source inspection, not an explicit "do it this way for a shared multi-tenant target" doc — no such doc exists) — flagged explicitly below wherever this applies.

## Recommended Stack

### Core Technologies

| Technology | Version | Purpose | Why Recommended |
|------------|---------|---------|-----------------|
| Supabase CLI | **2.117.0** (latest, confirmed via `npx supabase@latest --version`, 2026-09-21) | `db dump` for schema/data extraction from `ziko`; `db push`/`psql` for applying to `portfolio` | Official tool, wraps `pg_dump`/`pg_restore` in a version-matched container so client tooling never mismatches the Postgres server version. Confirmed current in Supabase's own CLI reference (`supabase.com/docs/reference/cli/*`, updated for 2026). |
| PostgreSQL client tools (`psql`, `pg_dump`, `pg_restore`) | Match target Postgres major version (Supabase projects are currently Postgres 15/17 — verify via Dashboard > Project Settings > Infrastructure for both `ziko` and `portfolio` before starting; a mismatch here is the #1 documented cause of `db dump`/`db push` failures) | Direct-connection dump/restore for the `public` schema tables (data volume: 39 users' worth of exercises/nutrition/coach data, 1318 exercises, 1495 supplements, 3106 supplement prices — small enough for a single `pg_dump`/`psql` pass, no need for logical replication) | Supabase's own "Backup and Restore using the CLI" guide (`supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore`) documents this exact roles→schema→data sequence as the supported path for project-to-project migration on Postgres of any version. |
| Supabase Admin API (`supabase-js` `auth.admin.createUser`, or equivalent `POST {url}/auth/v1/admin/users` REST call) | `@supabase/supabase-js` v2 (any current v2.x — the `admin.createUser` surface and its `id` field have been stable) | Re-creating `auth.users` (+ matching `auth.identities`) rows in `portfolio` **with the original `ziko` UUIDs preserved**, so every FK in the new `ziko_*` tables (`user_id`, `created_by_coach_id`, etc.) stays valid without touching a single foreign-key value | This is the one piece worth flagging as **verified beyond the docs**: the public TypeScript type `AdminUserAttributes` in `supabase/auth-js` (`src/lib/types.ts`) explicitly documents `id?: string — "Allows you to overwrite the default id set for the user."`, and the live GoTrue server handler (`supabase/auth`, `internal/api/admin.go`, `adminUserCreate`) parses `params.Id`, validates it as UUID, and sets `user.ID = customId` **before** the transactional insert — i.e. this is a first-class, currently-supported server behavior, not an undocumented hack. |
| Node.js script (custom, ~50–100 lines) using `pg` to read source `auth.users`/`auth.identities` + `@supabase/supabase-js` admin client to write target | Node 20 (matches repo's CI/Vercel Node version) | Orchestrates the per-user auth migration: read each `ziko` user row directly via Postgres connection (need `encrypted_password`, `email_confirmed_at`, `raw_user_meta_data`, `raw_app_meta_data`, `banned_until`, `phone` — none of which the Admin API exposes for reading), then call `admin.createUser({ id, email, password_hash, email_confirm, phone, user_metadata, app_metadata })` against `portfolio` | Because only 39 users are involved, a small imperative script beats a bulk SQL `COPY` into a shared `auth.users` table (see Alternatives/What NOT to Use) — it can dry-run, log every collision (duplicate email, invalid UUID), and be re-run idempotently (`createUser` fails cleanly per-row on conflict, it doesn't roll back a shared multi-tenant table). |

### Supporting Libraries

| Library | Version | Purpose | When to Use |
|---------|---------|---------|-------------|
| `bcrypt`-compatible `password_hash` param on `admin.createUser` | Built into GoTrue (documented in `auth-js` `AdminUserAttributes.password_hash`: "Supports bcrypt, scrypt (firebase), and argon2 password hashes") | Preserve athletes'/coaches' existing passwords with zero forced reset | Read `encrypted_password` straight from `ziko`'s `auth.users` via direct SQL (Supabase Auth stores it as a standard bcrypt hash, `$2a$`/`$2b$` prefix) and pass it through unmodified as `password_hash` on `createUser` against `portfolio`. Do **not** attempt to decrypt/re-hash it — bcrypt hashes are portable across GoTrue instances since both run the same algorithm. |
| `@supabase/supabase-js` Storage client (`storage.from(bucket).download()` / `.upload()`) | v2.x | Copy Storage objects (exercise-media, scan-photos, exports, and any coach-upload buckets) from `ziko` to `portfolio` bucket-by-bucket, object-by-object | Supabase does not support cross-project server-side bucket copy; the only supported path is a client-side download-then-reupload loop. Supabase's own community-referenced approach for this is a Colab/Node script that lists objects via the Storage API on the source, downloads each with the source's `service_role` key, and re-uploads with the target's `service_role` key. Note the documented **5 GB per-object cap** on this pattern (irrelevant here — GIFs/thumbnails/scan photos are all small) and that `storage.objects` DB rows are **not** copied by `pg_dump`'s default managed-schema exclusion — they get recreated naturally as a side effect of each upload. |
| Supabase Management API (`POST /v1/projects/{ref}/database/query`) | Current (`api.supabase.com/v1`) | Ad-hoc verification queries (row counts, spot-checks) against either project without opening a psql session; optionally, project settings automation (Vercel-style env var pushes are separate — this is DB-query only) | Use for **verification steps only** (e.g., `SELECT count(*) FROM ziko_user_profiles` post-migration), not for bulk data transfer — the endpoint is designed for single ad-hoc queries (same engine as the Dashboard SQL editor), returns opaque `{}`-shaped success responses, and Supabase does not document row/size limits for it. Bulk COPY-style data movement belongs in `psql`/`pg_dump`, not this API. |

### Development Tools

| Tool | Purpose | Notes |
|------|---------|-------|
| `supabase link` + `supabase db dump --db-url <conn>` | Extracts `ziko`'s `public`-schema roles/schema/data without needing a local Supabase stack | `db dump` **excludes `auth`, `storage`, and extension-created schemas by default** (confirmed via CLI reference) — this is actually desirable here: it means a plain `supabase db dump -f schema.sql` only touches the 93 Ziko application tables and will never accidentally emit `CREATE TABLE auth.users` or `CREATE TABLE storage.objects` statements that could collide with `portfolio`'s existing managed schemas. |
| A one-off **rename script** (Node/Python, not a Supabase tool — none exists) over the dumped `schema.sql` | Applies the `ziko_` prefix to every one of the 93 table names (and their sequences/indexes/constraints/policies) *before* the SQL is ever executed against `portfolio` | This is the step with no first-party tool. See Architecture note below — do the rename as a **text-level, whole-table-name substitution on the raw SQL dump**, not as post-hoc `ALTER TABLE ... RENAME`. Reason: several of Ziko's `SECURITY DEFINER` functions (`deduct_ai_credits`, `is_coach_of`, `record_athlete_decision`) and RLS policies almost certainly reference table names as literal identifiers inside plpgsql function bodies and policy `USING`/`WITH CHECK` expressions. Postgres resolves those identifiers **by name, via `search_path`, at each execution** for `SECURITY DEFINER`/plpgsql bodies — it does *not* rewrite function/policy body text when you `ALTER TABLE RENAME` after the fact. Renaming post-hoc silently breaks every function/policy that mentions the old name; renaming the dump text first (before any `CREATE FUNCTION`/`CREATE POLICY` statement is executed) fixes this at the source, in one pass, for schema, functions, triggers, and policies simultaneously. |
| `pg_dump --no-owner --no-privileges` flags | Keeps the dump portable across the two projects' differing internal role/owner setups | Confirmed in the official "Backup and Restore" guide as applied at dump time specifically to avoid Supabase-managed role conflicts on restore; apply this on **both** the schema dump and (if a raw `pg_dump` is used instead of `supabase db dump`) the data dump. |
| Session-mode Postgres connection (port 5432, direct or Session Pooler) — **not** the Transaction Pooler (port 6543) | Connection string used for every `pg_dump`/`psql`/`supabase db dump --db-url` invocation | Confirmed via Supabase's connection-pooling docs: the Transaction Pooler (6543) does not support prepared statements or long-lived sessions and is documented to interrupt/fail long-running `pg_dump` operations. Always grab the **Session pooler** or **direct connection** string from Dashboard > Project Settings > Database for both `ziko` and `portfolio`. |

## Installation

```bash
# Core — Supabase CLI (no global install needed, npx keeps it version-pinned per invocation)
npx supabase@latest --version   # confirm 2.117.0 or newer before starting

# Supporting — migration scripts (auth + storage orchestration)
npm install --no-save pg @supabase/supabase-js dotenv
# `pg` — direct Postgres reads from ziko (encrypted_password, raw_user_meta_data, etc.)
# @supabase/supabase-js — admin.createUser() writes against portfolio + Storage download/upload

# Dev dependencies — none beyond the above; this is a one-off ops script, not shipped app code
```

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|-------------|-------------|--------------------------|
| Admin API `createUser({ id, password_hash, ... })` per user, orchestrated by a small script | Raw `pg_dump --schema auth --data-only --use-copy` + `psql` COPY of `auth.users`/`auth.identities` directly into `portfolio` | Only if migrating into a **brand-new, empty** target project (the documented "migrating within Supabase" auth path assumes this). For a target that already has other tenants' rows in the *same* `auth.users` table (`portfolio`'s existing gecko/rh users), a raw COPY risks (a) `email` UNIQUE constraint collisions with existing rows going undetected until the whole transaction aborts, (b) `auth.identities` schema-shape mismatches if `ziko` and `portfolio` were provisioned on slightly different GoTrue/Postgres platform versions (the identities table's PK/shape has changed across GoTrue releases — copying rows blind assumes identical current shape), and (c) no per-row error isolation — one bad row can abort the batch. Only 39 users are involved, so the throughput advantage of bulk COPY is irrelevant; the Admin API's per-row validation and clean failure mode is worth more here. |
| Text-level `ziko_` rename on the raw `schema.sql` dump before execution | Post-hoc `ALTER TABLE public.<t> RENAME TO ziko_<t>;` for each table after restoring un-prefixed | Only if the schema had **no** functions/triggers/policies referencing table names as literal SQL text inside their bodies. Ziko's schema has `SECURITY DEFINER` RPCs and RLS-on-every-table by explicit project convention (see `CLAUDE.md`), so this condition does not hold — do the rename in the dump text, not after. |
| `supabase db dump` (CLI-wrapped `pg_dump`) | Raw `pg_dump`/`pg_restore` with manually-specified flags | Use raw `pg_dump`/`pg_restore` only if the two projects are on materially different Postgres major versions (rare for two live Supabase projects created within the same year) or if you need column-encryption/Vault key transfer, which the official backup-restore guide flags as requiring a separate out-of-band key transfer step regardless of which tool wraps `pg_dump`. |
| Storage: per-object download/reupload script | Supabase-managed "Restore to another project" / physical backup clone (`supabase.com/docs/guides/platform/clone-project`) | Only available on paid plans with **physical backups enabled**, and it clones an *entire* project (DB + storage + auth) into a **new** project — not an in-place merge into an already-populated multi-tenant project like `portfolio`. Not usable here regardless of plan, because the target already exists and hosts unrelated tenants. |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| Hand-editing/`INSERT`-ing directly into `portfolio`'s `auth.users` via the SQL Editor or a manual `INSERT` statement | `auth.users`/`auth.identities` are GoTrue-managed tables with triggers, generated columns, and cross-table invariants (identity `provider_id`/`identity_data` shape, `confirmed_at` generated from `email_confirmed_at`/`phone_confirmed_at` in current schema versions, audit log expectations) that a hand-written `INSERT` will not reliably reproduce. Getting this wrong on a **shared, already-populated** auth table risks corrupting login for `portfolio`'s existing gecko/rh users, not just Ziko's. | `admin.createUser()` — goes through GoTrue's own Go-level validation and identity-creation logic, so it's automatically correct for whatever GoTrue schema version `portfolio` is currently running. |
| Bulk `COPY`/`INSERT ... SELECT` of `auth.users` rows from `ziko` straight into `portfolio` in one shared-table transaction | Same shared-table risk as above, compounded by all-or-nothing failure semantics — a single duplicate email or malformed row aborts the whole batch and (if inside a larger transaction with schema/data restore) could roll back unrelated work | Per-user `admin.createUser()` calls in a script with try/catch per row, logging duplicates instead of aborting |
| Running `supabase db push` (migration replay) straight from `ziko`'s `supabase/migrations/` folder against `portfolio` | `db push` applies migrations **as originally named** — none of the 73 migration files reference `ziko_`-prefixed table names, so this would recreate `public.user_profiles`, `public.exercises`, etc. **unprefixed**, directly colliding with (or worse, silently coexisting confusingly alongside) `portfolio`'s own `rh_*`/`gecko_*`-prefixed but potentially unprefixed-adjacent naming, and violates the confirmed `ziko_` prefix decision outright | `supabase db dump` (data+schema, not migration replay) followed by the text-level rename pass described above, then apply the *renamed* SQL with `psql`/`db push` against a fresh migration file |
| Assuming `db dump`'s default schema dump captures `auth`/`storage` customizations (e.g., any Ziko-specific storage RLS policies on `storage.objects`) | `db dump` explicitly excludes `auth`, `storage`, and extension-created schemas by default (confirmed in the CLI reference) | Explicitly pass `--schema storage` (or `--schema auth,storage`) as a **separate, deliberate** dump pass if Ziko has custom `storage.objects` RLS policies (per `CLAUDE.md`: path-prefix RLS pattern using `(storage.foldername(name))[1]`) that need to be replicated onto `portfolio`'s buckets — review and manually merge these into `portfolio`'s existing `storage.objects` policy set rather than blind-applying a dump, since `storage.objects` is shared across all of `portfolio`'s tenants and a blanket policy could over-broaden access for gecko/rh objects too |

## Stack Patterns by Variant

**If a pre-flight check finds email overlap between `ziko`'s ~39 users and `portfolio`'s existing gecko/rh users:**
- Do not proceed with `createUser` for the colliding rows until a decision is made (this is a product/business decision, not a technical one — same person with two accounts vs. genuine collision)
- Because GoTrue's default configuration enforces a single unique `email` per Auth instance (not scoped per-app), this is the single most likely hard blocker in the whole migration — run the overlap check **first**, before writing any migration code: `SELECT email FROM ziko_auth_dump INTERSECT SELECT email FROM portfolio.auth.users;`

**If `ziko` and `portfolio` are found to be on different Postgres major versions (check Dashboard > Settings > Infrastructure on both):**
- Use raw `pg_dump`/`pg_restore` with explicit `--no-owner --no-privileges` and consult Supabase's "Migrate from Postgres to Supabase" guide's version-compatibility notes rather than `supabase db dump`, which assumes the CLI's bundled Postgres version matches both ends reasonably closely

**If any Ziko `SECURITY DEFINER` function or RLS policy references `auth.uid()` directly (expected, per `CLAUDE.md`'s standard RLS pattern):**
- No change needed — `auth.uid()` resolves against whatever `auth.users` row is authenticated in the *current* project at call time, and since the migration preserves the original UUIDs, `auth.uid() = ziko_user_profiles.user_id` continues to hold true post-migration with zero policy edits required. This is the core reason ID-preservation is non-negotiable rather than a nice-to-have.
